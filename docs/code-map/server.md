# Code map: server

All under `server/src/`.

- `index.ts`: the worker entry; sends `/auth/*` and `/api/*` to `auth.ts`, the rest to the rooms, exports the Durable Object classes, and runs the daily cron (`scheduled`: expired sessions and sign-ups, then `shipSweep.ts`). Hands `auth.ts` a `revokeSeats` that tells the account's newest ship to drop an ended session's seat tokens.
- `auth.ts`: the `/auth/*` and `/api/*` router, a Hono app (#324) behind `handleAuth` (which returns null for other paths); keep its routes in one chain, which the typed client will read. Also Google and Discord sign-in, sessions and display names over HTTP (#283, #284): OAuth start and callback (state cookie, linking a second provider), pending sign-ups until the name is confirmed, `/api/me`, `/api/signup`, `/api/rename`, `/auth/logout`, dev sign-in (`/auth/dev`, #287: `DEV_SERVER` and a localhost host only), `currentSession` (renews when under 15 days remain) and `sessionCookie` (for the Matchmaker). Rate-limits every route but logout and the OAuth callback first (#305, `allowAuthRequest`), keyed by account when the request has a valid session. Ending a session (logout, or another account signing in) revokes its seat tokens (`revokeSeats`); the account stays aboard. Cookies and the flow are in `docs/ops/sign-in.md`.
- `setupRoutes.ts`: posted setups over HTTP (#233), handlers routed by `auth.ts` after its rate limits: `GET /api/setups` (the newest version of every setup that validates, plus `mine` when signed in), `GET /api/setups/<id>` (any version, read leniently: `knobs` is null once it stops validating; `standard` returns `STANDARD_SETUP`) and `POST /api/setups` (needs an account; strict body, text through `moderateSetupTexts`). Reading is public. Never sends an account ID.
- `setupStore.ts`: the `setups` table in D1 (#233). Each post is one `INSERT ... SELECT` holding every check (50 new setups and 500 posts per account, the previous version's owner), and a unique index on `previous_id` refuses a second successor (`not_latest`). The owner's display name is joined in from `accounts` when read.
- `http.ts`: `json` and `readJsonBody` (JSON only, size checked from Content-Length before reading) for the HTTP routes.
- `oauth.ts`: each provider's authorize and token URLs, PKCE (Google), and reading the user ID and name; the client IDs and secrets come from `env`.
- `Matchmaker.ts`: one per lobby language (`matchmaker/en|fr|es`). Boards each joiner straight onto the language's open ship (`GameRoom.join`, one join at a time), launching a new one when there is none or it closed; remembers the open ship (`open` in storage) and forgets it when full or at its deadline (alarm). Sends watchers how many are aboard. No bots. Multiplayer needs an account (#285): the session cookie's hash is kept per connection and checked against D1 on joining (`sign_in_required`); the seat takes the account's display name; `account_ships` is written before the seat and deleted if the seat is refused (closed if the join threw); a failure while boarding answers `join_failed` so the socket can retry; an account with an open row is resumed on that ship (`GameRoom.resume`) or freed if the ship says it isn't aboard. A `singlePlayer` message instead launches a new room for that player alone (`GameRoom.setupSinglePlayer`).
- `GameRoom.ts`: one per game (`game-room/<uuid>`). `join` (the matchmaker's RPC) launches an empty ship in pre-selection on the first call, with that call's setup (`shipOverrides`: revalidated, the knobs plus `setupId`) and boards each player with a `join` input, returning their token and when the ship closes; `setup` seats everyone at launch (tests); `setupSinglePlayer` launches a single-player game (stored `singlePlayer`: no clock cycles, `nextCycleAt` null). `?token=` maps a connection to a seat; tokens, connections and bots are keyed by seat (`PlayerState.mind`) and resolved to the seat's current body with `bodyOf` on each use, since a Transfer moves seats between bodies. Persists state and the replay record to DO storage (`STATE_VERSION`), sends each connection its own `viewFor` (with the server's `now`), stamps actions with `at` and fires `tick` inputs from a storage alarm at `nextDue` and `cycle` inputs at each clock boundary (`cycleClock.ts`), reports connected seats to the rules as `seen` inputs with the server time, on connecting (only when it is news: inactive, or not seen since this clock cycle began) and just before each clock cycle (`markSeen`; inactivity, #145; it pushes views only when it ends someone's inactivity), and gives each `cycle` input its boundary time, runs bots (only when idle; `afterBotTurn` sends `botsPaused` changes and retries paused model bots with backoff), takes a single-player human's own model key (`setModel`/`clearModel`, outside `act()`, memory only, dropped when their last connection closes; `keyChanges` reschedules a bot whose turn spanned a key change), and handles chat (rate limit, moderation, `sendChat`). Accounts (#285): `accounts` (seat to account ID, beside the game, never in it), `aboard` (seats whose `account_ships` row is open; `releaseAccounts` closes a dead body's row after each input and all of them at the end), `tokenSessions` (token to session hash, for `revokeSession`), plus the `resume` and `seatAccounts` RPCs. The record also keeps `account:<seat>` (the account that took the seat, written with its join, never rewritten, kept when a version bump drops the snapshot) and each `chat` input's message id (`RecordedInput.chatId`), so a report can name the account and cite the message after a rename or once the state has trimmed it (#292). The `leaveShip` message (a cheat, `ALLOW_CHEATS` only, never an input) closes the seat's row, drops its tokens and closes its sockets with 4001; the character stays aboard. The action rate limit is per seat.
- `cycleClock.ts`: the cycle clock (#24): 3-hour cycles aligned to midnight GMT, or `CYCLE_SECONDS` in dev; which cycle of the day a time falls in.
- `bots.ts`: the `Bot` interface, the scripted `WanderBot` and `LogParrotBot`, and `ModelBot` (asks a model to choose from its view's affordable actions; anything else, and the scripted fallback decides). Bots live here, not in `shared`, because model-backed bots need network calls, secrets, and a spend cap.
- `prompt.ts`: pure. `buildPrompt(view)` (the model bot's prompt, built only from its own view, chat quoted as data), `parseChoice`, and `describeLogEntry`.
- `model.ts`: the OpenAI-compatible `completeOpenAi` client and `ModelGate`, one per game: credentials, call budget (persisted as `modelCalls`), in-flight limit, timeout, dropping a key the provider rejects, and `pause` (why its bots wait: `unavailable`, `key`, `budget`; null without a key). A 200 with an empty reply returns "" (the bot falls back); 400 and 404, like 401–403, stop the key until a new one is set (#224). `playerModelCredentials` maps an allowed provider (`MODEL_PROVIDERS` in `shared/src/protocol.ts`) to its fixed base URL for a player's own key (BYOK), and `setCredentials` swaps keys, ignoring failures from calls the old key made. No hosted default: the only other credentials are a dev key (`MODEL_*` in `server/.dev.vars`, with `DEV_SERVER`); `MODEL_BOTS` there seated model bots, but multiplayer no longer seats bots, so nothing reads it now.
- `rateLimit.ts`: the per-seat `RateLimiter` (in a Durable Object's memory), and `allowAuthRequest` for `/auth/*` and `/api/*` (#305): Cloudflare's rate-limiting bindings `AUTH_LIMIT`, `SIGNUP_LIMIT` and `SETUP_POST_LIMIT` (#233), keyed by account or client IP, spread over `AUTH_DEV_SCALE` keys on dev and test servers, and letting requests through if a binding fails. Limits and routes in `docs/ops/sign-in.md`.
- `accountStore.ts`: account storage in D1 (#282), with `setupStore.ts` the only code with SQL: accounts (unique ignoring case) and their sign-in identities, renames with `name_history`, sessions (stored as the SHA-256 of the session ID), and `account_ships` (at most one open ship per account, by a partial unique index). Async and batch-shaped like D1: atomic writes go in one `batch()`, never BEGIN/COMMIT. Takes a `SqlDatabase` (the part of `D1Database` it uses); `accountStoreFor(env)` wraps `env.DB`. Also pending sign-ups (`signups`) and `deleteExpired` for the cron, and `openShips` for the sweep. Used by `auth.ts`, the Matchmaker, `GameRoom` and `shipSweep.ts`.
- `shipSweep.ts`: the daily repair of `account_ships` (#285): open rows older than `SWEEP_GRACE_MS` whose ship doesn't list the account in `seatAccounts` are closed. Schema in `server/migrations/`; migrations and restores in `docs/ops/d1-runbook.md`.
- `testing/fakes.ts`: `FakeServer`, fake storage and sockets, so tests run without the Durable Object runtime.
- `scripts/model.trial.ts` (with `vitest.trial.config.ts`, `run-trial.mjs`): development only, `npm run model-trial -w server`. A headless single-player game with real model bots, for measuring cost, latency and replies (#224).

## STATE_VERSION and the shape fingerprint

The stored `game` snapshot leaves out `config`: it keeps the game's `ConfigOverrides` (shared/src/types/config.ts) instead, and `onStart()` resolves the config again with `resolveConfig` (shared/src/config.ts), so a live game picks up edits to `DEFAULT_CONFIG` on its next load while the `setup` record keeps the launch config and overrides. Anything per game that must survive a reload belongs in `ConfigOverrides`; config fields derived from it are recomputed by `resolveConfig`. `GameState.config` is typed `DeepReadonly`, so rules can't write to it (a write would be lost on reload); state that changes during a game, like each room's equipment, lives in `GameState`. A ship stores its whole `PreselectionRules` in its overrides, so an edit to `PRESELECTION` doesn't move a live ship's deadline or seat count away from the matchmaker's. Fields `createGame` copies into the state at launch (start items, equipment, rooms, starting AP/MP/HP/morale, ship resources' starting values) don't change in a live game.

`STATE_VERSION` (exported from `GameRoom.ts`) must be bumped whenever the stored `GameState` or `ConfigOverrides` shape changes: a field added, removed, renamed, or moved between optional and required (values and logic don't count). Also bump when `resolveConfig` changes what it derives from an override key (a renamed key would silently fall back to the default in live games), and for a config change that live states can't follow, such as the default `cyclesPerDay` (it breaks the clock alignment). Ordinary `GameConfig` changes need no bump. Bumping ends every live game, since there is no migration: on restart the room drops its `game` snapshot but keeps the record (`setup`, `input:*`, `blocked:*`) for the replay, and as `retired` it refuses connections, `setup` and `join` (`ship_closed`, so the matchmaker launches a new ship) instead of launching over the record (#167). `server/tests/stateShape.test.ts` compares the sorted key paths of a freshly stored game (including `players`, `items`, `chat` and `channels`), plus a sample with every `ConfigOverrides` key (typed `Required`, so a new key doesn't compile until it's added there), with `server/tests/state-shape.json`, which also records the version. After bumping, refresh it with `UPDATE_STATE_SHAPE=1 npm test -w server -- stateShape.test.ts` (it refuses if the shape changed and the version did not). Optional fields that a fresh game never sets are not in the fingerprint.
