# Code map: server

All under `server/src/`.

- `index.ts`: the worker entry; sends `/admin/*` to `adminRoutes.ts`, `/auth/*` and `/api/*` (accounts, setups, finished games) to `auth.ts`, the rest to the rooms, exports the Durable Object classes, and runs the daily cron (`scheduled`: expired sessions and sign-ups, then both sweeps in `shipSweep.ts`). Hands `auth.ts` a `revokeSeats` that tells the account's newest ship to drop an ended session's seat tokens.
- `auth.ts`: the `/auth/*` and `/api/*` router, a Hono app (#324) behind `handleAuth` (which returns null for other paths); keep its routes in one chain: `web`'s typed client reads the routes from the app's type (`ApiType`, below). Handlers return `json`'s typed responses and declare bodies with `jsonBody`, so the client knows both. Every route is also in the OpenAPI document (`openapi.ts`); a test fails if the two differ. Also Google and Discord sign-in, sessions and display names over HTTP (#283, #284): OAuth start and callback (state cookie, linking a second provider), pending sign-ups until the name is confirmed, `/api/me`, `/api/signup`, `/api/rename`, `/auth/logout`, dev sign-in (`/auth/dev`, #287: `DEV_SERVER` and a localhost host only), `currentSession` (renews when under 15 days remain) and `sessionCookie` (for the Matchmaker). Rate-limits every route but logout and the OAuth callback first (#305, `allowAuthRequest`), keyed by account when the request has a valid session. Ending a session (logout, or another account signing in) revokes its seat tokens (`revokeSeats`); the account stays aboard. Cookies and the flow are in `docs/ops/sign-in.md`.
- `setupRoutes.ts`: posted setups over HTTP (#233), handlers routed by `auth.ts` after its rate limits: `GET /api/setups` (the newest version of every setup that validates, plus `mine` when signed in), `GET /api/setups/<id>` (any version, read leniently: `knobs` is null once it stops validating; `standard` returns `STANDARD_SETUP`) and `POST /api/setups` (needs an account; strict body, text through `moderateSetupTexts`). Reading is public. Never sends an account ID.
- `setupStore.ts`: the `setups` table in D1 (#233). Each post is one `INSERT ... SELECT` holding every check (50 new setups and 500 posts per account, the previous version's owner), and a unique index on `previous_id` refuses a second successor (`not_latest`). The owner's display name is joined in from `accounts` when read. `ballot(ids)` returns those of the ids on the ballot (newest version, still validating) for the Matchmaker's vote round (#236).
- `http.ts`: `json` (a Response typed with its body and status for the typed client, `JsonResponse`), `readJsonBody` (JSON only, size checked from Content-Length before reading) and `jsonBody` (middleware that parses a route's body and declares its type; it never answers, the handler gets `body: T | null` and decides) for the HTTP routes.
- `apiSchemas.ts`: the site API's bodies as zod schemas (#324), registered under their names in the OpenAPI document. `{ name }` bodies are parsed with theirs (`parseNameRequest`); a setup post is still parsed by shared's `parsePostSetup`, whose rules are the game's. The types stay in shared: `SchemasMatchShared` fails the typecheck when a schema and its shared type differ. Import zod as `import * as z from "zod"` (a lint rule): the `z` export pulls all of zod, every locale included, into the Worker.
- `openapi.ts`: the OpenAPI 3.1 document (`/api/openapi.json`, the paths written out, the schemas from `z.toJSONSchema`) and the Scalar docs page (`/api/docs`, its script from a CDN at a pinned version), both only where `ALLOW_CHEATS` is set (`npm run dev` and the test deployment); production and staging answer 404.
- `apiTypes.ts`: `ApiType`, the site API's type for `web`'s `hc` client (#324). `npm run api-types -w server` emits its declarations (`tsconfig.api.json`, into the gitignored `dist/api-types`), exported as `@mush2/server/api` (types only, no JavaScript); `web`'s typecheck runs it first. `web` can't read the server's source directly: it needs the Workers types, which clash with the DOM's.
- `oauth.ts`: each provider's authorize and token URLs, PKCE (Google), and reading the user ID and name; the client IDs and secrets come from `env`.
- `Matchmaker.ts`: one per lobby language (`matchmaker/en|fr|es`). Boards each joiner straight onto the language's open ship (`GameRoom.join`, one join at a time), launching a new one when there is none or it closed; remembers the open ship (`open` in storage) and forgets it when full or at its deadline (alarm). Sends watchers how many are aboard. No bots. Multiplayer needs an account (#285): the session cookie's hash is kept per connection and checked against D1 on joining (`sign_in_required`); the seat takes the account's display name; `account_ships` is written before the seat and deleted if the seat is refused (closed if the join threw); a failure while boarding answers `join_failed` so the socket can retry; an account with an open row is resumed on that ship (`GameRoom.resume`) or freed if the ship says it isn't aboard. A `resume` message (#320, the lobby's Resume button) does only that: `matched`, or `not_aboard` when there is no open row or the ship says the account isn't aboard. A `singlePlayer` message instead launches a new room for that player alone (`GameRoom.setupSinglePlayer`). Also the language's vote round (#236): `vote` messages from signed-in accounts (`vote:<accountId>` in storage), totals broadcast as `votes`, each account's own as `myVote`. `shipClosed` runs on every open-to-closed transition (fill, deadline alarm, `closeIfExpired`, a join refused as closed, a `refresh` that finds it closed): it drops the ship and takes the votes before awaiting, so a round is counted once, and `closeRound` looks the voted setups up (`SetupStore.ballot`), tallies them (`tallyVotes`) and stores the winner as `nextSetup`, which the next launching join gets; a launch waits for `closing`.
- `GameRoom.ts`: one per game (`game-room/<uuid>`). `join` (the matchmaker's RPC) launches an empty ship in pre-selection on the first call, with that call's setup (`shipOverrides`: revalidated, the knobs plus `setupId`) and boards each player with a `join` input, returning their token and when the ship closes; `setup` seats everyone at launch (tests); `setupSinglePlayer` launches a single-player game (stored `singlePlayer`: no clock cycles, `nextCycleAt` null). `?token=` maps a connection to a seat; tokens, connections and bots are keyed by seat (`PlayerState.mind`) and resolved to the seat's current body with `bodyOf` on each use, since a Transfer moves seats between bodies. Persists state and the replay record to DO storage (`STATE_VERSION`), sends each connection its own `viewFor` (with the server's `now`), stamps actions with `at` and fires `tick` inputs from a storage alarm at `nextDue` and `cycle` inputs at each clock boundary (`cycleClock.ts`), reports connected seats to the rules as `seen` inputs with the server time, on connecting (only when it is news: inactive, or not seen since this clock cycle began) and just before each clock cycle (`markSeen`; inactivity, #145; it pushes views only when it ends someone's inactivity), and gives each `cycle` input its boundary time, runs bots (only when idle; `afterBotTurn` sends `botsPaused` changes and retries paused model bots with backoff), takes a single-player human's own model key (`setModel`/`clearModel`, outside `act()`, memory only, dropped when their last connection closes; `keyChanges` reschedules a bot whose turn spanned a key change), and handles chat (rate limit, moderation, `sendChat`). `onMessage` dispatches by the message groups in `shared/src/protocol.ts`: social messages go to `social()`, every other type to one entry of the typed `handlers` map. Accounts (#285): `accounts` (seat to account ID, beside the game, never in it), `aboard` (seats whose `account_ships` row is open; `releaseAccounts` closes a dead body's row after each input and all of them at the end), `tokenSessions` (token to session hash, for `revokeSession`), plus the `resume` and `seatAccounts` RPCs. Running ships (#431): after launch the room writes its `ships` row without awaiting it (`recordShip`), retried from the alarm with backoff (`shipRetry`, a `Backoff`) and on start while `shipRecorded` (saved with the next input) is false; an ended game writes none. `recordFinished` waits for a write under way, then deletes the row with the `games` row. The `running` RPC answers the sweep (true for a ship this build can't read). The record also keeps `account:<seat>` (the account that took the seat, written with its join, never rewritten, kept when a version bump drops the snapshot) and each player chat message's id (`RecordedInput.chatId`), so a report can name the account and cite the message after a rename or once the state has trimmed it (#292). Each input entry also carries its change to the full view (`RecordedInput.history`, `historyStep`, #335), in the same storage write as the input (no extra row), taken from `lastFull`, the full view after the last input since the room started; null after a start, so the next input carries the view as loaded. The list of finished games (#155): the room learns its lobby `language` from the matchmaker (`join`, `setupSinglePlayer`), notes each seat's role and character when the Mush are chosen (`starts`, `noteStarts`), stamps `endedAt` when the game ends, and then writes its entry once (`recordFinished`, after `releaseAccounts`); `listed` in the snapshot records that it's done, and a failed write is retried from the alarm with backoff (`listRetry`). Then it copies the history and moderator data (`raw`, `blocked`, `rateLimited`) to R2 (`copyReplay`, `replayStore.ts`, #336, #339): `replayReady` in the snapshot once every chunk, `moderation.json`, and the index are written, retried apart from the listing (`replayRetry`), and on start for an ended game not yet copied. 48 hours (`RECLAIM_DELAY_MS`) after both `listed` and `replayReady` are true, `reclaim.dueAt` fires `reclaimStorage`: verifies R2 via `verifyReplay` (skipped for unrecorded single-player games), deletes all DO storage (`deleteAll()`) but a `reclaimed` tombstone that keeps the room retired after eviction, closes open sockets with `4001`, and retries with backoff on failure (#339). Games stored before the list existed are never listed. A single-player game takes its player's account, if signed in, only for that entry (never `aboard`). The `leaveShip` message (a cheat, `ALLOW_CHEATS` only, never an input) closes the seat's row, drops its tokens and closes its sockets with 4001; the character stays aboard. The action rate limit is per seat.
  - Room log read state (#513): `logRead:<seat>` in room storage (outside the snapshot and the record), loaded in `onStart`; `connectedFrom` (in memory) notes where each seat's first open connection began. `connectLogRead` sends `logUnread` after the view on a human seat's connect, `disconnectLogRead` saves `live` when its last connection closes, `saveLiveLogReads` every 60 s after an input, and `logRead` messages (behind `readLimiter`, 12 per 10 s, shared with `chatRead`) raise the point and echo it to the seat's other connections. Bots skipped; deleted on Leave ship and cleared on reclaim.
  - Private notes (#503): `notes`, one entry per seat in room storage (`notes:<seat>`, outside the snapshot and the record), loaded whole in `onStart`, sent as `notes` on connect to a human seat, written by `writeNote` (bots refused, `noteLimiter` 20 per 10 s, `note_refused` for an edit `applyNoteEdit` refuses, echoed to the seat's other connections), deleted on Leave ship and cleared on reclaim. Keyed by seat, so they follow a Transfer.
- `cycleClock.ts`: the cycle clock (#24): 3-hour cycles aligned to midnight GMT, or `CYCLE_SECONDS` in dev; which cycle of the day a time falls in.
- `replayStore.ts`: `copyReplay(storage, bucket, meta)` pages through the room's `input:*` and `blocked:*` records, writes each gzipped chunk (`shared/src/replayChunks.ts`) to the `REPLAYS` R2 bucket as soon as the next starts, then `moderation.json` (#339, #157), then the index. Idempotent by key; no progress state. `verifyReplay(bucket, roomId, inputs)` verifies `index.json`, every chunk (input total matching `inputs`), and `moderation.json` before `GameRoom` deletes room storage.
- `bots.ts`: the `Bot` interface (with optional `refused`, called when a bot's action or social message is refused, `wake`/`woken`/`takeMessage` for chat, and `takeSocial` for a goal's message that isn't an action, sent through `GameRoom.social`, #417), the scripted `WanderBot` and `LogParrotBot`, `GoalBot` (follows the solo goals, choosing by priority; `BOT_AP_RESERVE`), and `ModelBot` (a `GoalBot` whose model chooses the goal from a numbered list, or `help` with parameters, plus at most one chat message a turn, dropped if it repeats its own last line (`repeatsLastMessage`); woken by chat it is asked even mid-goal and may carry on; without a key, on a garbage reply, past `MODEL_CHOICES_PER_CYCLE` or after `MODEL_CONSECUTIVE_MALFORMED_LIMIT` bad replies it goes by priority). `BOT_CHAT_CHAIN_DEPTH` bounds reply chains (#223); `GameRoom.wakeBots` (through the chat router, `router.ts`) and `botSay` do the waking and posting; `listens` says whether a bot can be woken. Bots live here, not in `shared`, because model-backed bots need network calls, secrets, and a spend cap.
- `bots/duties.ts`: `BOT_DUTIES` (#222): what each skill and title makes a bot do (`DutyTrigger`, `priority`, `prompt`), plus `dutyPriority`, `holdsTrigger` and `dutyPrompts`.
- `bots/goals/`: pure goals (`docs/plans/bot-goals.md`), one file per goal with its own `priority`, listed in `index.ts` (`SOLO_GOALS`, `END_CYCLE`); `types.ts` (`Goal`, `GoalDef`, `GoalStep` with its `social` step, `BotSocial`, `BotMemory`); - `bots/memoryStore.ts` (#440): bot memory in room storage. `BotMemorySnapshot` (plain data; `GoalBot.snapshot`/`restore` build and read it), one key per bot seat (`botMemoryKey`, `bot:<seat>`) written in `GameRoom.persist`'s put with `"game"` and read in `onStart` (`initBots`); `BOT_MEMORY_VERSION`: another version's snapshot is dropped, fields added since come out at a fresh bot's value. Never in game state, the record or a view.
- `bots/planetShare.ts` (#417, #421): the bots' shared-planet format, `formatPlanetShare` and `parsePlanetShare` (only bots parse shared text, and only this format), and the Commander's jump-hold lines in global chat (`HOLD_JUMP_LINE` "Jump: hold", `JUMP_NOW_LINE` "Jump: now", which grounds the Pilots, `CANCEL_HOLD_LINE` "Jump: off"), folded by `ChatLine.seq` into `BotMemory.jump` (`observeJump`, #427, so a hold survives its line scrolling out of chat; "off" also clears `holdSince`) and read through `holdStartCycle`, `isHoldingJump`, `isJumpDue`, `jumpNowCycle`; machine lines that wake no bot in `GameRoom.social`; and `crewAboard` (the minimap shows nobody in a patrol ship or the Icarus; `travel` waits for it up to `JUMP_WAIT_CYCLES`, 2).
- `bots/itemShare.ts` (owner, 2026-11-13): how bots tell each other where things lie. A fixed global-chat line, `Item: <type> in <ROOM>` or `Item: no <type> in <ROOM>` (`formatItemLine`, `parseItemLine`; types in `SHARED_ITEMS`: metal scrap and, #429, working extinguishers). `observeItems`, called by `GoalBot` each turn, folds new lines and the floor of the bot's own room into `BotMemory.items` and returns the line to post when chat doesn't say what the bot sees; `roomsHolding` is what goals read. `GameRoom.social` wakes no bot for an item line (no router call).
- `bots/fireShare.ts` (#429, #444): how bots find fires together. The alert bar (`view.alerts.fires`) gives the true count and `view.burningRooms` the reported rooms; the one fixed global-chat line is `Fire: clear in <ROOM>` for a searched room (`formatFireLine`, `parseFireLine`). `observeFires`, called by `GoalBot` each turn before `observeItems`, folds them, NERON's `fireStarted` notices (which restart the search) and the bot's own room into `BotMemory.fires` (`active`, `burning`, `checked`); it returns the line to post and whether there is news, which drops a current goal other than `extinguish` when that goal has something to do. `GameRoom.social` wakes no bot for a fire line either. `GoalBot` reports any fire or broken equipment it stands next to (`report_fire`, `report_equipment`) as a reflex before its goal.
- `bots/moraleShare.ts` (#452): the fixed global-chat line `Morale: low`, which a bot posts once when its own morale drops to `SELF_CARE_MORALE` (5) or less, and again only after recovering. `observeMorale` runs in `GoalBot` with the other line observers and folds askers into `BotMemory.morale` (`requests`: who asked, and how many comforts this Shrink gave them). - `bots/tankShare.ts` (#443): how bots find and share out broken oxygen tanks. `TANK_ROOMS` comes from the public ship map (owner, 2026-11-14); NERON's `equipmentBroken` for `OXYGEN_TANK` makes every tank room a suspect until seen, reports on the alert bar locate broken ones, and two fixed global-chat lines (`Tank: going to <ROOM>` claims a room for the cycle, `Tank: fine in <ROOM>` clears a suspect; `formatTankLine`, `parseTankLine`) split the work. `observeTanks` runs after `observeFires` in `GoalBot` and folds all of it into `BotMemory.tanks` (`broken`, `suspect`, `claims`); its news drops a current goal other than `extinguish` or `repairOxygen`. `GameRoom.social` wakes no bot for a tank line. The survival report counts broken tank-cycles and tank repairs.
- `bots/machineLines.ts`: `isMachineLine`, whether a chat line is one of the bots' fixed formats above (item, fire, tank, jump-hold); `GameRoom.social` wakes no bot for one. A new bots' line format is added there.
- `bots/skillChoice.ts`: `BOT_SKILL_RULES` (the owner's skill list for bots) and `chooseSkill`.
- `router.ts`: pure. The chat wake router (#341): `routerInput` (a message, its channel's last lines and readers with given names and public titles; only what the channel's readers see), `buildRouterPrompt` and `parseRouterReply` (`WAKE:` names, only candidates, at most `ROUTER_MAX_WAKES`; anything else wakes nobody). `GameRoom.wakeBots` calls it through the `ModelGate` for every non-private channel.
- `prompt.ts`: pure. `buildPrompt(view, options)` (the model bot's prompt: its own view, with rooms, equipment, items, skills and crew by display name in the ship's language (shared `names.ts`; goal labels name rooms by id and the prompt renders them), chat quoted as data with AI authors marked, the channels it can post in, when to ask for help, and the goals open to it by their labels, with "carry on" as 0 when woken mid-goal), `parseReply` (`GOAL:`, `HELP:` and `SAY:` lines, each checked against the view; anything malformed is null), and `describeLogEntry`.
- `log.ts`: the only log lines (#430): `logWarn`/`logError` write one JSON line with a fixed `LogEvent` and only safe `LogFields` keys, checked at compile time by `log.typecheck.ts`. What may and may not be logged is in `docs/ops/observability.md`.
- `model.ts`: the OpenAI-compatible `completeOpenAi` client and `ModelGate`, one per game: credentials, call budget (persisted as `modelCalls`), in-flight limit, timeout, dropping a key the provider rejects, and `pause` (why its bots wait: `unavailable`, `key`, `budget`; null without a key). A 200 with an empty reply returns "" (the bot falls back); 400 and 404, like 401–403, stop the key until a new one is set (#224). `playerModelCredentials` maps an allowed provider (`MODEL_PROVIDERS` in `shared/src/protocol.ts`) to its fixed base URL for a player's own key (BYOK), and `setCredentials` swaps keys, ignoring failures from calls the old key made. No hosted default: the only other credentials are a dev key (`MODEL_*` in `server/.dev.vars`, with `DEV_SERVER`); `MODEL_BOTS` there seated model bots, but multiplayer no longer seats bots, so nothing reads it now.

## Stored state across deploys (normalizers and `STATE_VERSION`)

The stored `game` snapshot leaves out `config`: it keeps the game's `ConfigOverrides` (shared/src/types/config.ts) instead, and `onStart()` resolves the config again with `resolveConfig` (shared/src/config.ts), so a live game picks up edits to `DEFAULT_CONFIG` on its next load while the `setup` record keeps the launch config and overrides. Anything per game that must survive a reload belongs in `ConfigOverrides`; config fields derived from it are recomputed by `resolveConfig`. `GameState.config` is typed `DeepReadonly`, so rules can't write to it (a write would be lost on reload); state that changes during a game, like each room's equipment, lives in `GameState`. A ship stores its whole `PreselectionRules` in its overrides, so an edit to `PRESELECTION` doesn't move a live ship's deadline or seat count away from the matchmaker's. Fields `createGame` copies into the state at launch (start items, equipment, rooms, starting AP/MP/HP/morale, ship resources' starting values) don't change in a live game.

On load, `onStart()` runs the upgrade steps the snapshot still needs (`upgrade`), then puts it through the normalizers (`normalizeOverrides`, `normalizeGame`, `normalizeSeatStarts`; shared/src/normalizeState.ts, #384), which keep only known fields and drop every action under way and queued. If it dropped any (`hasQueues`), `recordDropped` records one `dropQueues` input without applying it, so the record still rebuilds the stored state; it carries the view as loaded (`base`, no change). Nobody is told; they press again. A snapshot this build can't read (stored by a newer build, above `STATE_VERSION`, or one the normalizers reject) is kept, never deleted: the room is `unavailable` and logs `UNAVAILABLE` with `console.error`. It closes sockets with code 4002 ("Ship unavailable"; the client goes back to the lobby), `join` answers `ship_closed`, `setup` throws, `resume` answers `{ ok: false, unavailable: true }` (the matchmaker keeps the account's `account_ships` row and sends `ship_unavailable`), and `seatAccounts` throws so the daily sweep leaves its rows alone. A later build that reads it loads it on the next start, and players resume. Every copy of the view the room records in the history carries its `BuildStamp` (`STATE_VERSION` and `RULES_VERSION`).

How a stored shape changes (#384; the rules for the file are in the header of `shared/src/normalizeState.ts`, and the `rule` skill repeats them): **a new field** (in `GameState`, a nested struct, or `ConfigOverrides`, required or optional) gets a default in its normalizer, `added(raw, key, default)`, right for a game in progress and taken from the game's own data or its config; a `next*` counter is rebuilt from its data. It needs no `STATE_VERSION` change, and doesn't compile until its normalizer lists it (`AllKeys`). A new struct gets its own normalizer; a new union variant gets a case in its `switch`. **A removal, a rename, a changed type or meaning, a renamed or removed registry id, or a change to what `resolveConfig` derives from an override key** bumps `STATE_VERSION` and adds an `upgradeTo<N>` step to `UPGRADE_STEPS`, declaring the `paths` and `ids` it changes, always, even when no test asks (a field added after the fixtures were taken isn't in them). Ordinary `GameConfig` changes need neither. Registry keys (`ITEM_TYPES`, `SKILLS`, ...) are permanent internal ids: change what players see in `names.*.json` and the locales instead. The action queue is dropped on load, so a changed `Action` shape needs no step for live games (replay frames keep their queues and read as "too old" if `viewFor` can't). A breaking step lands in a deploy of its own (`docs/ops/deploy.md`: roll back only to a build with the same `STATE_VERSION`). To end every live game on purpose, raise `MIN_STATE_VERSION` (114, the first version with the normalizers): a snapshot stored below it is dropped on restart, the record (`setup`, `input:*`, `blocked:*`) is kept for the replay, and as `retired` the room refuses connections, `setup` and `join` (`ship_closed`, so the matchmaker launches a new ship) instead of launching over the record (#167). `server/tests/storedRooms.test.ts` (#384) loads the committed fixtures in `server/tests/stored/` (whole `StoredRoom`s taken at a `STATE_VERSION`: arriving, in orbit, two players mid-action; never refreshed) and rooms generated at test time (`storedRooms.ts`, a seeded random game steered to the same moments): every stored value survives the load unless an upgrade step declares its path (`UpgradeStep.paths`) or it is the dropped queue; every id in the registry snapshot (`v<N>-registries.json`) still exists unless a step declares it (`UpgradeStep.ids`); a `__probe` key on every struct is dropped; loading is idempotent; and a `GameRoom` loads each, serves every seat's view and replay frame, and passes a cycle. `WRITE_STORED_FIXTURES=1 npm test -w server -- storedRooms.test.ts` writes the moments missing at the current version, never overwriting one.
