# Code map: server

All under `server/src/`.

- `index.ts`: the worker entry; sends `/auth/*` and `/api/*` (accounts, setups, finished games) to `auth.ts`, the rest to the rooms, exports the Durable Object classes, and runs the daily cron (`scheduled`: expired sessions and sign-ups, then `shipSweep.ts`). Hands `auth.ts` a `revokeSeats` that tells the account's newest ship to drop an ended session's seat tokens.
- `auth.ts`: the `/auth/*` and `/api/*` router, a Hono app (#324) behind `handleAuth` (which returns null for other paths); keep its routes in one chain: `web`'s typed client reads the routes from the app's type (`ApiType`, below). Handlers return `json`'s typed responses and declare bodies with `jsonBody`, so the client knows both. Every route is also in the OpenAPI document (`openapi.ts`); a test fails if the two differ. Also Google and Discord sign-in, sessions and display names over HTTP (#283, #284): OAuth start and callback (state cookie, linking a second provider), pending sign-ups until the name is confirmed, `/api/me`, `/api/signup`, `/api/rename`, `/auth/logout`, dev sign-in (`/auth/dev`, #287: `DEV_SERVER` and a localhost host only), `currentSession` (renews when under 15 days remain) and `sessionCookie` (for the Matchmaker). Rate-limits every route but logout and the OAuth callback first (#305, `allowAuthRequest`), keyed by account when the request has a valid session. Ending a session (logout, or another account signing in) revokes its seat tokens (`revokeSeats`); the account stays aboard. Cookies and the flow are in `docs/ops/sign-in.md`.
- `setupRoutes.ts`: posted setups over HTTP (#233), handlers routed by `auth.ts` after its rate limits: `GET /api/setups` (the newest version of every setup that validates, plus `mine` when signed in), `GET /api/setups/<id>` (any version, read leniently: `knobs` is null once it stops validating; `standard` returns `STANDARD_SETUP`) and `POST /api/setups` (needs an account; strict body, text through `moderateSetupTexts`). Reading is public. Never sends an account ID.
- `setupStore.ts`: the `setups` table in D1 (#233). Each post is one `INSERT ... SELECT` holding every check (50 new setups and 500 posts per account, the previous version's owner), and a unique index on `previous_id` refuses a second successor (`not_latest`). The owner's display name is joined in from `accounts` when read.
- `http.ts`: `json` (a Response typed with its body and status for the typed client, `JsonResponse`), `readJsonBody` (JSON only, size checked from Content-Length before reading) and `jsonBody` (middleware that parses a route's body and declares its type; it never answers, the handler gets `body: T | null` and decides) for the HTTP routes.
- `apiSchemas.ts`: the site API's bodies as zod schemas (#324), registered under their names in the OpenAPI document. `{ name }` bodies are parsed with theirs (`parseNameRequest`); a setup post is still parsed by shared's `parsePostSetup`, whose rules are the game's. The types stay in shared: `SchemasMatchShared` fails the typecheck when a schema and its shared type differ. Import zod as `import * as z from "zod"` (a lint rule): the `z` export pulls all of zod, every locale included, into the Worker.
- `openapi.ts`: the OpenAPI 3.1 document (`/api/openapi.json`, the paths written out, the schemas from `z.toJSONSchema`) and the Scalar docs page (`/api/docs`, its script from a CDN at a pinned version), both only where `ALLOW_CHEATS` is set (`npm run dev` and the test deployment); production and staging answer 404.
- `apiTypes.ts`: `ApiType`, the site API's type for `web`'s `hc` client (#324). `npm run api-types -w server` emits its declarations (`tsconfig.api.json`, into the gitignored `dist/api-types`), exported as `@mush2/server/api` (types only, no JavaScript); `web`'s typecheck runs it first. `web` can't read the server's source directly: it needs the Workers types, which clash with the DOM's.
- `oauth.ts`: each provider's authorize and token URLs, PKCE (Google), and reading the user ID and name; the client IDs and secrets come from `env`.
- `Matchmaker.ts`: one per lobby language (`matchmaker/en|fr|es`). Boards each joiner straight onto the language's open ship (`GameRoom.join`, one join at a time), launching a new one when there is none or it closed; remembers the open ship (`open` in storage) and forgets it when full or at its deadline (alarm). Sends watchers how many are aboard. No bots. Multiplayer needs an account (#285): the session cookie's hash is kept per connection and checked against D1 on joining (`sign_in_required`); the seat takes the account's display name; `account_ships` is written before the seat and deleted if the seat is refused (closed if the join threw); a failure while boarding answers `join_failed` so the socket can retry; an account with an open row is resumed on that ship (`GameRoom.resume`) or freed if the ship says it isn't aboard. A `resume` message (#320, the lobby's Resume button) does only that: `matched`, or `not_aboard` when there is no open row or the ship says the account isn't aboard. A `singlePlayer` message instead launches a new room for that player alone (`GameRoom.setupSinglePlayer`).
- `GameRoom.ts`: one per game (`game-room/<uuid>`). `join` (the matchmaker's RPC) launches an empty ship in pre-selection on the first call, with that call's setup (`shipOverrides`: revalidated, the knobs plus `setupId`) and boards each player with a `join` input, returning their token and when the ship closes; `setup` seats everyone at launch (tests); `setupSinglePlayer` launches a single-player game (stored `singlePlayer`: no clock cycles, `nextCycleAt` null). `?token=` maps a connection to a seat; tokens, connections and bots are keyed by seat (`PlayerState.mind`) and resolved to the seat's current body with `bodyOf` on each use, since a Transfer moves seats between bodies. Persists state and the replay record to DO storage (`STATE_VERSION`), sends each connection its own `viewFor` (with the server's `now`), stamps actions with `at` and fires `tick` inputs from a storage alarm at `nextDue` and `cycle` inputs at each clock boundary (`cycleClock.ts`), reports connected seats to the rules as `seen` inputs with the server time, on connecting (only when it is news: inactive, or not seen since this clock cycle began) and just before each clock cycle (`markSeen`; inactivity, #145; it pushes views only when it ends someone's inactivity), and gives each `cycle` input its boundary time, runs bots (only when idle; `afterBotTurn` sends `botsPaused` changes and retries paused model bots with backoff), takes a single-player human's own model key (`setModel`/`clearModel`, outside `act()`, memory only, dropped when their last connection closes; `keyChanges` reschedules a bot whose turn spanned a key change), and handles chat (rate limit, moderation, `sendChat`). Accounts (#285): `accounts` (seat to account ID, beside the game, never in it), `aboard` (seats whose `account_ships` row is open; `releaseAccounts` closes a dead body's row after each input and all of them at the end), `tokenSessions` (token to session hash, for `revokeSession`), plus the `resume` and `seatAccounts` RPCs. The record also keeps `account:<seat>` (the account that took the seat, written with its join, never rewritten, kept when a version bump drops the snapshot) and each `chat` input's message id (`RecordedInput.chatId`), so a report can name the account and cite the message after a rename or once the state has trimmed it (#292). Each input entry also carries its change to the full view (`RecordedInput.history`, `historyStep`, #335), in the same storage write as the input (no extra row), taken from `lastFull`, the full view after the last input since the room started; null after a start, so the next input carries the view as loaded. The list of finished games (#155): the room learns its lobby `language` from the matchmaker (`join`, `setupSinglePlayer`), notes each seat's role and character when the Mush are chosen (`starts`, `noteStarts`), stamps `endedAt` when the game ends, and then writes its entry once (`recordFinished`, after `releaseAccounts`); `listed` in the snapshot records that it's done, and a failed write is retried from the alarm with backoff (`listRetryAt`). Then it copies the history to R2 (`copyReplay`, `replayStore.ts`, #336): `replayReady` in the snapshot once every chunk and the index are written, retried apart from the listing (`replayRetryAt`), and on start for an ended game not yet copied. Games stored before the list existed are never listed. A single-player game takes its player's account, if signed in, only for that entry (never `aboard`). The `leaveShip` message (a cheat, `ALLOW_CHEATS` only, never an input) closes the seat's row, drops its tokens and closes its sockets with 4001; the character stays aboard. The action rate limit is per seat.
- `cycleClock.ts`: the cycle clock (#24): 3-hour cycles aligned to midnight GMT, or `CYCLE_SECONDS` in dev; which cycle of the day a time falls in.
- `replayStore.ts`: `copyReplay(storage, bucket, meta)` pages through the room's `input:*` record, writes each gzipped chunk (`shared/src/replayChunks.ts`) to the `REPLAYS` R2 bucket as soon as the next starts, then the index. Idempotent by key; no progress state.
- `bots.ts`: the `Bot` interface (with optional `refused`, called when a bot's action is refused, and `wake`/`woken`/`takeMessage` for chat), the scripted `WanderBot` and `LogParrotBot`, `GoalBot` (follows the solo goals, choosing by priority; `BOT_AP_RESERVE`), and `ModelBot` (a `GoalBot` whose model chooses the goal from a numbered list, or `help` with parameters, plus at most one chat message a turn; woken by chat it is asked even mid-goal and may carry on; without a key, on a garbage reply, past `MODEL_CHOICES_PER_CYCLE` or after `MODEL_CONSECUTIVE_MALFORMED_LIMIT` bad replies it goes by priority). `BOT_CHAT_CHAIN_DEPTH` bounds reply chains (#223); `GameRoom.wakeBots` (through the chat router, `router.ts`) and `botSay` do the waking and posting; `listens` says whether a bot can be woken. Bots live here, not in `shared`, because model-backed bots need network calls, secrets, and a spend cap.
- `bots/duties.ts`: `BOT_DUTIES` (#222): what each skill and title makes a bot do (`DutyTrigger`, `priority`, `prompt`), plus `dutyPriority`, `holdsTrigger` and `dutyPrompts`.
- `bots/goals/`: pure goals (`docs/plans/bot-goals.md`), one file per goal with its own `priority`, listed in `index.ts` (`SOLO_GOALS`, `END_CYCLE`); `types.ts` (`Goal`, `GoalDef`, `GoalStep`, `BotMemory`); `blocks.ts` (`goTo`, `find`, `travelAp`, `canAfford`, `roomsWith` over the public `SHIP_ROOMS`); `work.ts` (`workAt`, shared by the work goals); `snoop.ts` (a Scrapper snoops where it stands); `tendPlants.ts` (a Botanist-role bot tends the garden; `BotMemory.today` holds once-a-day keys, cleared on a new day); `astro.ts` (an Astrophysicist analyzes and scans planets once a day); `contactSol.ts` (a Radio Expert tries the Sol link while it is down); `commsOfficer.ts` (the Comms Officer decodes rebel calls, contacts Xyloph and updates NERON while linked); `shrinkDorm.ts` (a Shrink spends the night in a dormitory once a day); `shootHunters.ts` (Shooter or Gunner) and `patrolShootHunters.ts` (a Pilot's sortie; `HUNTER_GOALS` in `index.ts` are what interrupt a rest). `BotMemory.scripted` is true for a bot that goes by priority, which gets higher AP thresholds for shooting.
- `bots/skillChoice.ts`: `BOT_SKILL_RULES` (the owner's skill list for bots) and `chooseSkill`.
- `router.ts`: pure. The chat wake router (#341): `routerInput` (a message, its channel's last lines and readers with given names and public titles; only what the channel's readers see), `buildRouterPrompt` and `parseRouterReply` (`WAKE:` names, only candidates, at most `ROUTER_MAX_WAKES`; anything else wakes nobody). `GameRoom.wakeBots` calls it through the `ModelGate` for every non-private channel.
- `prompt.ts`: pure. `buildPrompt(view, options)` (the model bot's prompt: its own view, chat quoted as data with AI authors marked, the channels it can post in, when to ask for help, and the goals open to it by their labels, with "carry on" as 0 when woken mid-goal), `parseReply` (`GOAL:`, `HELP:` and `SAY:` lines, each checked against the view; anything malformed is null), and `describeLogEntry`.
- `model.ts`: the OpenAI-compatible `completeOpenAi` client and `ModelGate`, one per game: credentials, call budget (persisted as `modelCalls`), in-flight limit, timeout, dropping a key the provider rejects, and `pause` (why its bots wait: `unavailable`, `key`, `budget`; null without a key). A 200 with an empty reply returns "" (the bot falls back); 400 and 404, like 401–403, stop the key until a new one is set (#224). `playerModelCredentials` maps an allowed provider (`MODEL_PROVIDERS` in `shared/src/protocol.ts`) to its fixed base URL for a player's own key (BYOK), and `setCredentials` swaps keys, ignoring failures from calls the old key made. No hosted default: the only other credentials are a dev key (`MODEL_*` in `server/.dev.vars`, with `DEV_SERVER`); `MODEL_BOTS` there seated model bots, but multiplayer no longer seats bots, so nothing reads it now.
- `rateLimit.ts`: the per-seat `RateLimiter` (in a Durable Object's memory), and `allowAuthRequest` for `/auth/*` and `/api/*` (#305): Cloudflare's rate-limiting bindings `AUTH_LIMIT`, `SIGNUP_LIMIT` and `SETUP_POST_LIMIT` (#233), keyed by account or client IP, spread over `AUTH_DEV_SCALE` keys on dev and test servers, and letting requests through if a binding fails. Limits and routes in `docs/ops/sign-in.md`.
- `gameStore.ts`: finished games in D1 (#155, `0004_games.sql`): `games` and `game_players` (each seat's account, name at the time, start and end character and role, alive). `finishedEntry` (pure) builds the rows only from an ended game, and skips a single-player game without an account; `recordFinished` is one `batch()` of `INSERT OR IGNORE`, so a retry changes nothing; `replayAccess` says whether a listed game is single player and which accounts played it (for the replay routes only); `listFinished` pages multiplayer games newest first by a `(ended_at, room_id)` cursor (`encodeCursor`/`decodeCursor`), so games that end meanwhile don't shift the pages. Never returns an account ID.
- `gameRoutes.ts`: `GET /api/games?before=&limit=` (#155), routed by `auth.ts` after its rate limits: public, multiplayer only; a cursor it didn't make is a 400 `invalid_cursor`.
- `replayRoutes.ts`: `GET /api/games/<id>/replay` (the index) and `/replay/<n>` (a chunk, its stored gzip passed through) (#337), routed by `auth.ts` after its rate limits, reading only R2 (`REPLAYS`, `AuthDeps.replays`). Served only when the game is listed (`GameStore.replayAccess`; only ended games are) and its R2 index exists (the copy's confirmation): 409 `not_ready` without the index, 404 otherwise. Single player: only the account that played it (`mayView`, where share links would go), else the same 404; `no-store`. Public chunks are immutable-cached.
- `accountStore.ts`: account storage in D1 (#282), with `setupStore.ts` and `gameStore.ts` the only code with SQL: accounts (unique ignoring case) and their sign-in identities, renames with `name_history`, sessions (stored as the SHA-256 of the session ID), and `account_ships` (at most one open ship per account, by a partial unique index). Async and batch-shaped like D1: atomic writes go in one `batch()`, never BEGIN/COMMIT. Takes a `SqlDatabase` (the part of `D1Database` it uses); `accountStoreFor(env)` wraps `env.DB`. Also pending sign-ups (`signups`) and `deleteExpired` for the cron, and `openShips` for the sweep. Used by `auth.ts`, the Matchmaker, `GameRoom` and `shipSweep.ts`.
- `shipSweep.ts`: the daily repair of `account_ships` (#285): open rows older than `SWEEP_GRACE_MS` whose ship doesn't list the account in `seatAccounts` are closed. Schema in `server/migrations/`; migrations and restores in `docs/ops/d1-runbook.md`.
- `testing/fakes.ts`: `FakeServer`, fake storage and sockets, so tests run without the Durable Object runtime.
- `scripts/model.trial.ts` (with `vitest.trial.config.ts`, `run-trial.mjs`): development only, `npm run model-trial -w server`. A headless single-player game with real model bots, for measuring cost, latency and replies (#224).

## STATE_VERSION and the shape fingerprint

The stored `game` snapshot leaves out `config`: it keeps the game's `ConfigOverrides` (shared/src/types/config.ts) instead, and `onStart()` resolves the config again with `resolveConfig` (shared/src/config.ts), so a live game picks up edits to `DEFAULT_CONFIG` on its next load while the `setup` record keeps the launch config and overrides. Anything per game that must survive a reload belongs in `ConfigOverrides`; config fields derived from it are recomputed by `resolveConfig`. `GameState.config` is typed `DeepReadonly`, so rules can't write to it (a write would be lost on reload); state that changes during a game, like each room's equipment, lives in `GameState`. A ship stores its whole `PreselectionRules` in its overrides, so an edit to `PRESELECTION` doesn't move a live ship's deadline or seat count away from the matchmaker's. Fields `createGame` copies into the state at launch (start items, equipment, rooms, starting AP/MP/HP/morale, ship resources' starting values) don't change in a live game.

`STATE_VERSION` (exported from `GameRoom.ts`) must be bumped whenever the stored `GameState` or `ConfigOverrides` shape changes: a field added, removed, renamed, or moved between optional and required (values and logic don't count). Also bump when `resolveConfig` changes what it derives from an override key (a renamed key would silently fall back to the default in live games), and for a config change that live states can't follow, such as the default `cyclesPerDay` (it breaks the clock alignment). Ordinary `GameConfig` changes need no bump. Bumping ends every live game, since there is no migration: on restart the room drops its `game` snapshot but keeps the record (`setup`, `input:*`, `blocked:*`) for the replay, and as `retired` it refuses connections, `setup` and `join` (`ship_closed`, so the matchmaker launches a new ship) instead of launching over the record (#167). `server/tests/stateShape.test.ts` compares the sorted key paths of a freshly stored game (including `players`, `items`, `chat` and `channels`), plus a sample with every `ConfigOverrides` key (typed `Required`, so a new key doesn't compile until it's added there), with `server/tests/state-shape.json`, which also records the version. After bumping, refresh it with `UPDATE_STATE_SHAPE=1 npm test -w server -- stateShape.test.ts` (it refuses if the shape changed and the version did not). Optional fields that a fresh game never sets are not in the fingerprint.
