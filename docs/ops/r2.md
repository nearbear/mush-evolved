# R2: replay storage

When a game ends, its room copies the game's history (`RecordedInput.history`, #335) to R2 (#336). Replays are served only from R2 (#337), so showing one never wakes the room. Room storage is kept after the copy; retention is #132.

## Buckets

One bucket per deployment, bound as `REPLAYS` in `server/wrangler.jsonc` (environments don't inherit bindings, so each repeats it):

| Deployment | Bucket |
| --- | --- |
| Production | `mush2-replays-production` |
| Staging | `mush2-replays-staging` |
| Test | `mush2-replays-test` |

`npm run dev` needs nothing: `wrangler dev` simulates the bucket locally (under `server/.wrangler/state`).

## Setup (once per account)

1. Enable R2 in the Cloudflare dashboard (R2 Object Storage). The free tier needs a payment method on file; it covers 10 GB-month, 1M Class A (writes) and 10M Class B (reads) operations a month.
2. Create the buckets, in `server/`. **They must exist before the next deploy, or the deploy fails.**

   ```sh
   npx wrangler r2 bucket create mush2-replays-production
   npx wrangler r2 bucket create mush2-replays-staging
   npx wrangler r2 bucket create mush2-replays-test
   ```

3. For the CI deploy to test (`deploy.md`), add **Account > Workers R2 Storage: Edit** to the Cloudflare API token, since a deploy checks the bucket it binds.

The buckets stay private: no public access or custom domain. The Worker reads them through the binding.

## What a copy holds

Keys depend only on the game, so a retried copy rewrites the same objects (idempotent, nothing read first). Under `replays/<roomId>/v<HISTORY_VERSION>/`:

- `chunk-000000.json.gz`, `chunk-000001.json.gz`, …: one per cycle, gzipped (`contentEncoding: gzip`, so it can go to a browser as is). Each is a JSON array of `{ at, history }`, one per input. Chunk 0 runs from launch to the first cycle; each starts at a full copy of the view, so it rebuilds by itself (`rebuildHistory`). Only the history leaves the room: never the input, text before moderation, message ids, accounts or blocked text.
- `index.json`, written last: `{ v, roomId, rulesVersion, endedAt, seats, chunks }`. `seats` is each seat's role and character when the Mush were chosen (no names); each chunk entry is `{ cycle, firstInput, inputs, from, to }`.

The format is `shared/src/replayChunks.ts`; the writer is `server/src/replayStore.ts`. A bump of `HISTORY_VERSION` writes under a new prefix.

## Copy and retry

`GameRoom.copyReplay` runs after the input that ends the game, from the alarm, and on a room start for an ended game whose copy isn't done. `replayReady` in the room's snapshot is set only once every chunk and the index were written. A failure (R2 down, or no binding) logs `Copying the replay failed: …` and retries from the alarm, after 1 minute and doubling up to an hour, independently of the games list (#155).

A game is ~0.26 MB gzipped and a few dozen writes per copy (one per cycle plus the index).

## Inspecting a copy

In `server/`, with another deployment's bucket name for staging or test, or `--local` in place of `--remote` for `npm run dev`'s copy:

```sh
npx wrangler r2 object get mush2-replays-production/replays/<roomId>/v1/index.json --pipe --remote
npx wrangler r2 object get mush2-replays-production/replays/<roomId>/v1/chunk-000000.json.gz --pipe --remote | gunzip | head -c 2000
```

The room ID is the `id` in the games list (`GET /api/games`). Delete a copy with `npx wrangler r2 object delete <bucket>/<key> --remote`; nothing yet deletes one automatically (#132).
