# R2: replay storage

When a game ends, its room copies the game's history (`RecordedInput.history`, #335) and moderator-only text (`moderation.json`, #339, #157) to R2 (#336). Replays are served only from R2 (#337, below), so showing one never wakes the room. 48 hours after both `listed` (#155) and `replayReady` are set, the room verifies its R2 objects and deletes its Durable Object storage, all but a one-key tombstone (#339); R2 retention itself is #132.

## Buckets

One bucket per deployment, bound as `REPLAYS` in `server/wrangler.jsonc` (environments don't inherit bindings, so each repeats it):

| Deployment | Bucket |
| --- | --- |
| Production | `mush2-replays-production` |
| Staging | `mush2-replays-staging` |
| Test | `mush2-replays-test` |

`npm run dev` needs nothing: `wrangler dev` simulates the bucket locally (under `server/.wrangler/state`).

## Setup (once per account)

1. Enable R2 in the Cloudflare dashboard (R2 Object Storage). The free tier needs a payment method on file; it covers 10 GB-month, 1M Class A (writes) and 10M Class B (reads) operations a month.
2. Create the buckets, in `server/`. **They must exist before the next deploy, or the deploy fails.**

   ```sh
   npx wrangler r2 bucket create mush2-replays-production
   npx wrangler r2 bucket create mush2-replays-staging
   npx wrangler r2 bucket create mush2-replays-test
   ```

3. For the CI deploy to test (`deploy.md`), add **Account > Workers R2 Storage: Edit** to the Cloudflare API token, since a deploy checks the bucket it binds.

The buckets stay private: no public access or custom domain. The Worker reads them through the binding.

## What a copy holds

Keys depend only on the game, so a retried copy rewrites the same objects (idempotent, nothing read first). Under `replays/<roomId>/`:

- `chunk-000000.json.gz`, `chunk-000001.json.gz`, …: one per cycle, gzipped (`contentEncoding: gzip`, so it can go to a browser as is). Each is a JSON array of `{ at, history }`, one per input. Chunk 0 runs from launch to the first cycle; each starts at a full copy of the view, so it rebuilds by itself (`rebuildHistory`). Only the history leaves the room for the public replay: never the input, text before moderation, message ids, accounts or blocked text.
- `moderation.json`, written before the index: `{ v, roomId, raw, rawByInput, blocked, rateLimited }` (#339, #157). `raw` maps `ChatMessage.id` (`RecordedInput.chatId`) to text before the filter changed it; `rawByInput` maps input sequence numbers (`input:<seq>`) for filtered inputs without a `chatId` (channel/thread names, planet/report shares); `blocked` holds `blocked:*` in order; `rateLimited` holds each seat's rate-limit count. Never served by the public replay routes.
- `index.json`, written last: `{ v, roomId, rulesVersion, endedAt, seats, chunks }`. `seats` is each seat's role and character when the Mush were chosen (no names); each chunk entry is `{ cycle, firstInput, inputs, from, to }`.

The format is `shared/src/replayChunks.ts`; the writer and verifier are `server/src/replayStore.ts`.

## Copy, retry, and room cleanup

`GameRoom.copyReplay` runs after the input that ends the game, from the alarm, and on a room start for an ended game whose copy isn't done. `replayReady` in the room's snapshot is set only once every chunk, `moderation.json`, and the index were written. A failure (R2 down, or no binding) logs `Copying the replay failed: …` and retries from the alarm, after 1 minute and doubling up to an hour, independently of the games list (#155).

Once both `listed` and `replayReady` are set, `GameRoom` schedules `reclaimAt` 48 hours later (`RECLAIM_DELAY_MS`). On that alarm, `GameRoom.reclaimStorage` finishes releasing any seat accounts, verifies R2 via `verifyReplay` (`index.json`, every chunk totaling the expected input count, and `moderation.json` — skipped only for unrecorded single-player games without an account), closes open sockets with `4001`, wipes the room with `ctx.storage.deleteAll()`, then writes one tombstone key (`reclaimed`), which `onStart` reads as `retired`, so a stale join or setup is refused even after eviction and can't launch a game that would overwrite the archived replay (#339). Verification or storage failures log `Reclaiming room storage failed: …` and retry from the alarm after 1 minute, doubling up to an hour.

A game is ~0.26 MB gzipped and a few dozen writes per copy (one per cycle plus `moderation.json` and the index).

## Serving a replay

`GET /api/games/<roomId>` (the game's summary, from D1 only, with the same privacy; #368), `GET /api/games/<roomId>/replay` (the index) and `GET /api/games/<roomId>/replay/<n>` (chunk `n`) read the bucket through the binding (`server/src/replayRoutes.ts`, #337); the room is never woken. `moderation.json` is never served by these routes. A replay is served only if the game is in the games list (D1: only ended games are) and its `index.json` exists (written last, so it confirms the copy). A listed game without an index answers 409 `not_ready`; anything else missing answers 404. A single-player replay goes only to the account that played it. A chunk goes out with its stored gzip (`Content-Encoding: gzip`); public chunks are cached as immutable, a public index for an hour, single-player answers never. Every request counts against `AUTH_LIMIT` (60 a minute), so a viewer should load chunks as it needs them, not all at once.

`HISTORY_VERSION` (`index.v`) versions only `HistoryStep` and `ViewDiff`; the viewer checks `index.v` and catches `HistoryError` from `rebuildHistory` or `perspective` when an older game's state shape is no longer readable.

## Inspecting a copy

In `server/`, with another deployment's bucket name for staging or test, or `--local` in place of `--remote` for `npm run dev`'s copy:

```sh
npx wrangler r2 object get mush2-replays-production/replays/<roomId>/index.json --pipe --remote
npx wrangler r2 object get mush2-replays-production/replays/<roomId>/chunk-000000.json.gz --pipe --remote | gunzip | head -c 2000
```

The room ID is the `id` in the games list (`GET /api/games`). Delete a copy with `npx wrangler r2 object delete <bucket>/<key> --remote`; nothing yet deletes one automatically (#132).
