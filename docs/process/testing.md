# What to test, and why

The project's main risks, roughly in priority order: hidden information leaking to the wrong seat, untrusted input (clients, chat, and later model output) getting further than it should, rules that quietly break as features are added, and the game stalling. Tests should go where those risks are. This is a checklist, not a coverage target.

Status: **covered** = tests exist, **partial** = some exist, **missing** = none yet. Tests live in a `tests/` folder next to `src/` in each package (`shared/tests`, `server/tests`, `tools/tests`, `web/tests`). Server tests (`server/tests/`) run `GameRoom` and `Matchmaker` under plain Vitest: `partyserver` is replaced by `FakeServer` via `vi.mock`, with fake storage and sockets in `server/src/testing/fakes.ts`. This doesn't exercise the real Durable Object runtime (`@cloudflare/vitest-pool-workers`, not installed; ask first). Most server risks can instead be tested by pulling the decision out into a pure function, as `server/src/rateLimit.ts` already does.

Keeping rules tests from breaking for the wrong reasons: shared helpers live in `shared/tests/support.ts` (seats, player lookup, applying actions, advancing cycles, and reading what a view offers through `offered`/`option`/`costOf`), so a change to `Seat`, `ActionResult`, or the shape of `PlayerView.actions` is fixed in one file. Tests derive balance numbers (costs, chances, amounts, weights, caps) from `state.config` and don't pin them: pinning is paused while balance is tuned (owner, 2026-11-06; bringing it back is [#381](https://github.com/nearbear/mush2/issues/381)). Rule data that isn't balance (research needs, skill lists, length limits, the log window) may still be pinned. Hidden-information tests are the exception and stay strict: they should break when a view field changes. The tests in `shared/tests` are not typechecked (`shared/tsconfig.json` includes only `src`), so a type error there shows up only when the test runs.

## Test cost

`npm run verify` runs every test, at the end of every task, so a slow test is paid many times a day. Budget: a single test under 1s and a file under 3s (`npm test -w <package> -- <file> --reporter=verbose` shows each test's time). To CPU-profile a slow test file (Vitest's `forks` pool does not forward `NODE_OPTIONS` to workers), pass Node's profiler via `--execArgv`: `npx vitest run -r <package> <file> --execArgv="--cpu-prof" --execArgv="--cpu-prof-dir=/tmp/prof"` (add `-t "<test>"` to isolate one test). Over that, tell the owner before it lands. `verify` warns on its own ([#383](https://github.com/nearbear/mush2/issues/383)): after `ok test` it prints a `slow` line for each test over `TEST_BUDGET_MS` and each file whose tests add up to more than `FILE_BUDGET_MS` (`tools/src/dev/slowTests.ts`), slowest first. It never fails the step, since timings are noisy. A file's time is the sum of its tests' durations, leaving out import and transform time, which swing with the cache. Files already over budget are in `SLOW_ALLOWED` there, each with its own ceiling (about 1.5x its time when listed) and a reason, so a `slow` line means a new slow test or an allowlisted file that got slower; shrink or drop an entry when a file speeds up. Ways to stay inside it: check a pure function directly instead of playing whole games to sample it (`rollWeighted` in `rng.test.ts`, not 2,000 snoops); shrink the config so the case comes sooner (the small log window in `replayView.test.ts`); share one recorded game across a file; and never call `expect` inside a loop over thousands of items (collect the failures, then assert once). Real-browser tests go in `tools/tests/browser/` and run with `npm run test:browser`, outside `verify`. The long random-game checks in `replay.test.ts` run on one seed in `verify` (except the replay rebuild and perspective checks, which run only in `npm run test:slow`, as they ran over budget or timed out under `verify`'s load); `npm run test:slow` (and CI, after `npm test`) runs them on five seeds, the perspective check with every seat at every step ([#382](https://github.com/nearbear/mush2/issues/382)). The seed count is `REPLAY_SEEDS`, read in `shared/tests/randomGame.ts`.

## 1. Hidden information (highest priority)

A leak can't be fixed after the fact: once a client has seen a role, the game is spoiled. Leaks also don't show up as bugs, since everything still looks fine on screen.

- **`viewFor` strips everything a seat shouldn't see:** other players' roles, HP, morale, and inventories; other rooms' items, equipment, and log history; private log entries; the RNG state. *Partial* (`rules.test.ts`, `items.test.ts`, `examine.test.ts`, plus targeted checks that contamination, spore state, and private log lines are in no other seat's view in `infection.test.ts`, `skills.test.ts`, and `heal.test.ts`; `death.test.ts` checks that a dead player's view has nothing room-based and no one else's role or contamination, and that nobody's view gives a dead player's room; `planets.test.ts` checks that another player's planets, scan failures, and your own unrevealed sector tags are in no view). The blunt test is in `leaks.test.ts`: every hidden value in a four-seat game is a unique sentinel, and each seat's serialized view must contain exactly the sentinels it may see, so a leak through a field nobody thought to check still fails. Every field of `GameState`, `PlayerState` and `ItemState` is listed in `shared/tests/leakFields.ts` with who may see it and the test that checks it; `leaks.test.ts` also checks that no view's log carries an id (one counter per game, so a gap would show a hidden line). A new field fails `leaks.test.ts` (keys of a real game) and `tools/tests/leaks/fields.test.ts` (the interfaces in the source, so optional fields too) until it is listed (#102). Values that can't be made unique (roles, enums, player ids, such as `cheats` or `room`) rely on the targeted test named there.
- **Error messages don't depend on hidden state.** `applyAction` and `queueAction` answer `illegal_action` whatever the reason (`rules.ts`, `queue.ts`), and the room passes on a generic error (`GameRoom*.test.ts`). A message like "can't target a Mush" would leak a role through the error channel. `errors.test.ts` (#103) checks refusals that turn on hidden state (spiking a Mush, the crew's daily spore cap, a partner who has already shared today) against ones that don't, both at once and queued, and first checks each case hits the refusal it names. It covers the error text only: that an action is refused at all can still give something away (see the note in the file). *Covered.*
- **Action bars and queues** (`queue.ts`): your action under way and your queue are in your view only; others get a `busy` bar (times, never the action) only in the actor's room and only when the action's log entry could reach them (private never, covert only on camera). *Covered* (`queue.test.ts`). Not covered, and not new: every accepted input, ticks included, re-sends a view to every connection, so message timing says that someone did something.
- **Channel plans** (`plans.ts`): only a channel's members get its plans, a stopped holder's reason is only in their own log, and the author's view after a summons has nothing about rooms but theirs. *Covered* (`plans.test.ts`, the `planRoom` sentinel in `leaks.test.ts`). The `postPlan` message: parsing with known keys only and malformed drafts refused (`protocol.test.ts`), recording, a non-creator refused, the chat rate limit and a rebuild from the record (`GameRoom*.test.ts`, "GameRoom plans").
- **Each connection gets its own seat's view** (`GameRoom.broadcastViews`). A mix-up here (one view sent to everyone, or the wrong `playerId` in a connection's state) would leak everything, and no rules test would catch it. *Covered* (`GameRoom*.test.ts`).
- **Seat tokens.** A missing or unknown token is rejected (close code 4001). A valid token maps to exactly one seat. The matchmaker sends each human only their own token, never a broadcast. A token is effectively the seat itself, so whoever holds it can play that seat and see its view. *Covered* (`GameRoom*.test.ts`, `Matchmaker.test.ts`).
- **Bots see only their own seat's view.** This is structural today (`viewFor(game, botId)` in `scheduleBots`; `WanderBot` is tested to pick only from its own view's legal actions in `bots.test.ts`). The model bot's prompt is tested to be unchanged by anything hidden from its seat (another player's role, HP and morale, another's private log entry, another room's history) and to change with the seat's own state (`model.test.ts`). *Covered.*

## 2. Untrusted input

Everything from a client is hostile until parsed. Player text will also become model input.

- **Wire parsers** (`parseGameMessage`, `parseMatchmakerMessage`): reject malformed JSON, wrong types, extra or unknown action kinds, and oversized strings, and never pass through fields that weren't validated; the 24-character name cap (`MAX_NAME_LENGTH`) is trimmed and enforced. *Covered* (`protocol.test.ts`).
- **Legality is the server's call.** `applyAction` rejects any action not in `legalActions(state, player)`, including well-formed actions for another player's item, a non-adjacent room, or a dead player. *Covered* (`legality.test.ts`: a short seeded walk where every offered action is accepted, and every action made by swapping an item, room or player id in one is accepted exactly when it is offered too; a dead player is refused everything. Each `applyAction` clones the state, so it checks only the acting player at each step: one seed in `verify` (about 0.4 s), five in `npm run test:slow`. `actions.test.ts` checks unaffordable and non-candidate actions; `punch`, `spike`, `death` and other feature tests check illegal uses leave state unchanged).
- **Chat moderation** (`moderateChat`): invisible characters, links, masked words, length limits. *Covered* for the basics. Grow the cases as abuse turns up.
- **Player names** are trimmed and capped at 24 characters (`parseMatchmakerMessage`) but not moderated (only chat goes through `moderateChat`). No view carries them during a game (people are known by character), but they will be shown once games can end. They go through `moderateChat` (as `moderateName`) when the end screen shows them (owner, 2026-10-22). *Covered* (`victory.test.ts`).
- **Rate limits:** the per-connection message limit, and a per-seat chat limit that survives reconnecting. *Covered* (`rateLimit.test.ts`, `GameRoom*.test.ts`). The sign-in and account routes (#305), with the binding faked: an OAuth start redirects with `rate_limited` before touching the provider, `/api/*` answers 429 with `Retry-After`, keys are the account when signed in and the IP otherwise (also for an expired session), only sign-ups count against the new-account limit, logout and the callback are never limited, dev servers spread keys, and a failing binding lets requests through. *Covered* (`auth.test.ts`). *Not covered:* the client keeping its account state on a 429 (`useMe`; no jsdom test renders it yet), and the real binding (checked on staging).
- **Model output:** garbage, an action that isn't legal, or a prompt-injection attempt has to end up as a legal fallback action, never an unchecked one. `parseReply` takes only a goal number in range, a `HELP:` whose task, person and room check out against the view, and a `SAY:` to a channel the bot can post in (or a living character), within the length limit; anything else posts nothing and `ModelBot` chooses by priority (or carries on); a chosen goal runs with no further calls until it ends or an interrupt fires; chat and private channel names can't break out of their quoted line in the prompt (`model.test.ts`). Model-written chat (#223): the chat router (#341) wakes only the bots it names, nobody on "nobody", a failed call or garbage, never more than `ROUTER_MAX_WAKES`, never the author or a non-reader, and sees only the channel's own lines and readers with no roles (`router.test.ts`, `GameRoom*.test.ts`); a private channel wakes its members without it; a reply chain stops at `BOT_CHAT_CHAIN_DEPTH`, replies are posted with `isBot` and moderated like a person's, and bots without a key are never woken (`GameRoom*.test.ts`); the `help` goal walks, fails when the person isn't there, and keeps the reserve unless told (`goals.test.ts`). *Covered.* Not covered: the per-seat chat rate limit on a bot, and opening a private channel "to" someone in a room test. `GoalBot` returns only actions its view offers, even when a goal's step is stale (`goals.test.ts`, including long seeded runs).

## 3. Rules correctness

The rules will grow the most (infection, win conditions), and every addition can break an older rule.

- **Each rule's numbers** (AP/MP costs and caps, cycle gains, slot counts, and the per-feature `cost`, `effect` and `successChance` values) against the confirmed values in `config.ts`. *Covered* for what exists; the feature tests read them from the nested `state.config`.
- **Determinism:** the same seed and inputs give the same state. Persistence and replays depend on it. *Covered* (`rules.test.ts` for the same seed, and `replay.test.ts`: random games across a day boundary, with chat and private channels, replayed from JSON-stored inputs must equal the live state, and a ship launched empty in pre-selection through its joins; a rejected input makes the replay throw. Every input type is generated except cheats, which `cheats.test.ts` replays, and `createThread`. `GameRoom*.test.ts` checks that the stored snapshot is exactly what `rebuildGame` makes of the stored record, with bots, ticks, a cycle and chat, so a state change that bypasses the record fails it).
- **The RNG moves on and rules read the game's own config.** A roll that drops the next RNG state repeats the same draw; a rule that reads `DEFAULT_CONFIG` ignores a game's own config. *Covered*: rule code draws through the `roll`, `rollInt`, `rollFloat` and `rollShuffle` helpers in `rng.ts`, which advance `state.rng` themselves (`rng.test.ts`); only seeded generators that take a bare seed (`planets.ts`, `createGame`, `singlePlayerGame`) use the pair functions, and return the next state to their caller; Biome bans importing `DEFAULT_CONFIG` in `shared/src` (only `singlePlayer.ts` may, with a `biome-ignore`); `cheatRoom.test.ts` checks the second for disease durations (the Superkube's ailment option).
- **No lucky seeds.** A test must not depend on a hard-coded seed happening to give an outcome: any new draw in setup or play shifts the rolls after it and breaks such a test (the drugs did, twice). Force the outcome instead: odds set to 0 or 1 in the game's config (`noIncidents`, `noHunters`, a feature's `dirtyChance: 0`), helpers like `forceDismantleOdds` (`support.ts`), state set directly (a token's `roll`, an event table), or a seed searched for at test time (`seedFor` and `CLEAN` in `research.test.ts`). A fixed seed is fine when the assertion holds for every seed (determinism, invariants). Setup draws roll on streams of their own (`streamFor` in `rng.ts`: the drugs and the Medlab stock), so adding one doesn't move `state.rng`; `rng.test.ts` checks that `createGame` leaves it where the role shuffle and first rebel call put it. To check a test: run it under a handful of other seeds; it should pass on all of them.
- **Every module loads on its own.** An import cycle crashes only when it is entered at the wrong module, which depends on what a test file imports first. *Covered* (`moduleLoad.test.ts` loads each `shared/src` file first into an empty module graph).
- **Purity:** `applyAction` never mutates its input, and failed actions leave the state unchanged. *Covered* (`rules.test.ts`, `items.test.ts`, and the per-feature tests).
- **State survives a JSON round trip** (`JSON.parse(JSON.stringify(state))` deep-equals the original). State is persisted and cloned via JSON, so an accidental `Map`, `Set`, `Date`, or `undefined` would silently corrupt games. *Missing.* Some tests copy state through JSON to check that an action doesn't mutate it, but none asserts that a round trip returns an equal state, and the persistence test uses fake storage that keeps the objects as they are.
- **Every legal action succeeds.** Anything in `legalActions` must be accepted by `applyAction`; the client and bots trust that list. *Partial* (feature tests apply the actions they expect to be offered; nothing walks the whole list).
- **0 HP always kills** (`death.test.ts`, plus `tools/tests/death/hpWrites.test.ts`, which scans the rules source and fails if any file outside its allowlist (`death.ts`, `cheats.ts`, `actions/heal.ts`, `actions/consume.ts`, `hunters.ts`) writes `.hp`). *Covered* for punch (`punch.test.ts`), hunger (`statuses.test.ts`), and showering (`shower.test.ts`).
- **Invariants under random play:** run many seeded games with `WanderBot`-style random legal actions and check after every step that each item is in exactly one container, AP and MP stay within their caps, nobody is in a room that doesn't exist, and the game always offers someone a legal action. This catches combinations nobody wrote a test for. *Missing.*

## 4. The server keeps the game going

A stalled or wiped game is the most visible failure for players.

- **Persistence:** a restarted room restores the game, tokens, and input count, and continues the input record; it drops every action under way and queued and records one `dropQueues` input, so the record still rebuilds the stored state and the history every view (#384; the rules-level equivalence is in `shared/tests/normalizeState.test.ts`); a save older than `MIN_STATE_VERSION` is dropped, not loaded half-broken, while its record (`setup`, inputs, blocked text) is kept and never launched over; a save this build can't read (stored by a newer build, or rejected by the normalizers) is kept untouched and the room refuses players as unavailable until a build that reads it starts. The snapshot stores config overrides, not the config, for every way a room launches, and a reload resolves the config again, picking up a `DEFAULT_CONFIG` edit but not a `PRESELECTION` one, and equipment changed during a game survives it. `FakeStorage` copies values in and out like Durable Object storage. *Covered* (`GameRoom*.test.ts`, `shared/tests/config.test.ts`; loading the committed snapshots of older versions is `server/tests/storedRooms.test.ts`). Restoring the bots after a restart is not tested.
- **Stored shape across deploys** (#384): a new field, struct or union variant doesn't compile until its normalizer handles it (`AllKeys`, the exhaustiveness `switch`), so it needs no `STATE_VERSION` change. Normalizing keeps every value of a populated game, round-trips every variant of every union, keeps a stored `null`, strips unknown keys, is idempotent, and never uses `??`; the upgrade steps run in order and a newer version throws (`shared/tests/normalizeState.test.ts`). Against the committed fixtures (`server/tests/stored/`, never refreshed, so the oldest runs every step) and a room generated at test time: every stored value survives the load unless a step declares its path, every snapshotted registry id still exists unless a step declares it, a `__probe` on every struct is stripped, and a `GameRoom` loads each, serves every seat's view and replay frame, and passes a cycle (`server/tests/storedRooms.test.ts`). *Covered.* Not caught: a removal or rename of a field added after the newest fixture, so a breaking change always gets a step by hand (`rule` skill).
- **Timed actions keep going:** an action is stamped with server time, an alarm is set for its end, and the alarm's tick does it; a room restored mid-action finishes it from the stored alarm; Clear queue removes the alarm. *Covered* (`GameRoom*.test.ts`; rules in `queue.test.ts`, replays with ticks in `replay.test.ts`). Bots waiting for their bar is not tested at the room level.
- **Bots never stall the game.** A bot isn't scheduled twice. A bot whose chosen action is illegal is logged (`console.warn`), told through `Bot.refused` (a `GoalBot` drops that goal for the cycle), and doesn't crash the room. A `decideAction` that throws or hangs needs a fallback. A throw inside the `setTimeout` in `scheduleBots` is caught and logged, and a bot stays pending until its decision finishes, so a slow model call isn't asked twice (tested). Model calls time out (`ModelGate`), and a failing model leaves model bots playing scripted (tested). A bot that throws is not tested at the room level. *Partial.*
- **Matchmaker:** the first player is boarded at once on a newly launched ship with no bots; later players join the same open ship; a full or closed ship is replaced by a new one; the deadline alarm forgets the open ship; the open ship survives a restart; simultaneous joiners board one at a time; each player gets only their own token; a taken character is refused. Vote round (#236): only signed-in accounts vote, for setups on the ballot, before or after joining; totals only to everyone and each account's own vote only to its sockets (no account ID in any message); the round closes on fill, at the alarm, and on a deadline that passed before the alarm (a late vote goes to the new round, a join launches with the winner); two refreshes seeing the close count it once; a tie is drawn at random; a superseded version's votes are ignored; the ship's actual setup is reported; votes and the next setup survive a restart; a D1 failure at the close carries the votes over. *Covered* (`Matchmaker.test.ts`; `tallyVotes` in `shared/tests/setups.test.ts`). Dev-only bot filling (`GameRoom.fillWithBots`) is not tested.

## 5. Data and tooling

- **Generated files are current:** `ship-art.json`, `ship-rooms.json`, and `ship-plan.json` match their sources, and `ship-map.json` is in its one-tile-per-line format. *Covered* (`tools/tests/shipLayout/`).
- **The ship map editor** (`web/src/editor/`): its scene is what the game draws at fog depth "all", it names each sprite's map tile and turns pixels into cells as `gridToPx` turned around (`shipScene.test.ts`); its edits change only what they should, keep the old map for undo, move by the arrow keys' screen directions, and pick a new tile's kind and room, and move a whole room (`edits.test.ts`); its checks find doors with no room, no floor or no way back, floor on floor and equipment with no tile, and point at the tile and cells to fix (`checks.test.ts`); a save is refused unless `validateMap` passes, which is tested on bad maps and run on the committed one (`tools/tests/shipLayout/shipLayout.test.ts`). *Covered.* The component (pan, zoom, selecting, saving through the dev server, the checks panel and jumping to a problem) was checked in a browser by hand, not by a test.
- **The ship map is sound:** every door goes both ways, and every room can be reached from the start room. *Covered* (`tools/tests/shipLayout/shipLayout.test.ts`, `rules.test.ts`). The minimap plan has the same doors as the rules' room graph.
- **Converter edge cases:** slices past their sheet, equipment bound to unknown slices. *Covered* (`shipLayout.test.ts`).
- **The hand-edited map is consistent:** every tile's slice and frame exist, equipment binds only known slices, doors have targets, no room overlaps another (`ship-check`), and no wall stops just short of another room's. *Covered* (`shipLayout.test.ts`, `check.test.ts`, `web/tests/iso/placement.test.ts`). Not covered: how it looks at fog depth 1 and 2, where rooms beyond aren't drawn.
- **Account storage** (`server/src/accountStore.ts`, D1): every migration applies in order to a fresh database and files are numbered without gaps; names are unique ignoring case; a failed statement in a batch leaves nothing behind (account plus identity, rename plus history); renames are limited to one per 24 hours and free the old name; an expired session cannot be renewed; only a session ID's SHA-256 is stored, and sessions expire, renew and delete; an account is aboard one ship at a time, and leaving or ending a ship frees it. *Covered* on node:sqlite (`accountStore.test.ts`, through `server/tests/sqliteD1.ts`, which has no exec or transactions so the store can't rely on them), plus a smoke test that applies the migrations with wrangler to a throwaway local D1 and runs each statement once on D1 itself (`accountStore.d1.test.ts`). Migrations are append-only: CI fails a push to `main` that modifies, renames or deletes one (`.github/workflows/ci.yml`).
- **Sign-in and display names** (`server/src/auth.ts`, `oauth.ts`; `shared/src/accounts.ts`): a callback whose state doesn't match the browser's cookie (or was started for another provider) is refused before contacting the provider; the state cookie is single-use; Google gets PKCE; no account exists until the name is confirmed; a suggested name that fails `checkDisplayName` or was taken starts empty; taken (ignoring case), rejected and empty names are refused; linking refuses an identity owned by another account and a session that changed since start; a session renews only under 15 days left and expires; logout is per device, POST only, and ends a pending sign-up; signing in with a new identity signs the device out first, and a known one ends a pending sign-up; one identity per provider per account; a body without `Content-Length` or over 1 KB is refused unread; rename once a day, freeing the old name, with `name_unchanged` not using up the day; deployment cookies are `__Host-` and Secure, dev ones port-named. *Covered* in `server/tests/auth.test.ts` with a fake provider on node:sqlite, and `shared/tests/accounts.test.ts`. *Not covered:* a real Google or Discord round trip (manual, once the owner's OAuth apps exist), and the Vite proxy (checked by hand: `/api`, `/auth` and the `/parties` WebSocket go through it, and wrangler sees the page's origin).
- **Setups** (#233; `shared/src/setups.ts`, `server/src/setupStore.ts`, `setupRoutes.ts`): strict parsing of knobs, per-language text and posts (unknown fields and languages refused); moderation masks the word list in every field and rechecks the caps after removing links; 50 new setups per account with versions free, 500 posts in all; versions number along the chain and only the owner's newest version gets one; the list shows only the newest version, and one that stops validating drops off it but is still found by ID; the owner's current name is shown; reading is public, posting needs an account and is rate limited per account; no response holds an account ID. The D1 smoke test runs each statement, including the unique-index error. *Covered* (`shared/tests/setups.test.ts`, `server/tests/setups.test.ts`, `accountStore.d1.test.ts`).
- **Dev sign-in** (#287): refused without `DEV_SERVER` (even with `ALLOW_CHEATS`), refused on a non-localhost host, never reaches an account through a Google or Discord identity, and reuses its account by name. *Covered* in `server/tests/auth.test.ts`.
- **Finished games list** (#155; `server/src/gameStore.ts`, `gameRoutes.ts`, `GameRoom.ts`): a running game produces no entry; a game is written once, and a failed write is retried from the alarm until it lands; start and end roles and characters are recorded across a conversion and a Transfer (alpha and beta Mush), and every seat is human at the start when the game ended before the Mush were chosen; a single-player game is recorded only with an account and never listed publicly; games stored before the list existed are never listed; paging is newest first and stable when a game ends between pages; the page size is capped; a cursor the server didn't make is refused; no response holds an account ID. The D1 smoke test runs each statement. *Covered* (`gameStore.test.ts`, `GameRoom*.test.ts`, `accountStore.d1.test.ts`). *Not covered:* the `/games` page (checked by hand), and a game ending through a real input in the room tests (they set the phase directly).
- **Replay copy to R2** (#336): a finished game's history is copied once, as per-cycle chunks that each rebuild by themselves and together rebuild the whole history and the game's last full view; a chunk holds only each input's time and history; `replayReady` stays false until every chunk and the index are written; a failed copy (partway or at the index) retries from the alarm, and a room revived after a failed copy finishes it; the record stays in room storage. *Covered* in `replay.test.ts` (chunking) and `GameRoom*.test.ts` (with `FakeR2Bucket`). *Not covered:* real R2 and workerd's `CompressionStream` (Node's runs in the tests); not yet tried on a deployment.
- **Replay API** (#337): a listed multiplayer game's index and chunks are served to anyone and cacheable; a running game (not listed, even with objects in R2) answers 404; a listed game without its index answers 409 `not_ready` and serves no chunk; a single-player replay goes only to its own account, `no-store`, and anyone else gets the same 404 as a missing game; chunks out of range or malformed are 404; gzip passes through, or is unzipped for a client that doesn't accept it. The summary (`GET /api/games/<id>`, #368): equal to the list's entry, cacheable when public, served before the copy is confirmed, 404 for a running game, single player only to its own account (`no-store`, no account ID). *Covered* in `replayRoutes.test.ts` (with `FakeR2Bucket`). *Not covered:* workerd's `encodeBody: "manual"` passing the stored gzip through unchanged (Node ignores it); not yet tried on a deployment.
- **Replay helpers** (#367): the event marks are exactly the steps that add a log line or message (by id sets) or start a cycle, over a recorded random 16-seat game of 1,958 inputs with room restarts, the same with or without the chunk before; a trim in the step that adds a line still marks it, a trim alone doesn't, a restart's base never does; `lineStep` finds the first step holding a line across chunks; all-seeing equals the seat's own view apart from log and chat, adds the room's hidden lines and the seat's own elsewhere but never another room's, keeps lines the full view dropped through the streams, and reveals each body's role, stats, inventory and contamination; `seatsAt` across a Transfer. *Covered* in `replayView.test.ts`. The `server/` import ban is a Biome rule (checked by hand that it fires); an `import * as` of the whole package would get past it.
- **Loading a replay** (#369): positions to chunks (the launch state in chunk 0), clamping a deep link; the settled chunk and the next are wanted, and nothing while dragging until the position settles, the last frame kept stale meanwhile; only the settled chunk and 2 each side kept, a late chunk for a position left behind ignored; the 409 backoff (1, 2, 4, 8, 15 s, then Retry), a 429's `Retry-After` and its never-ending backoff, a failed chunk's Retry; another history format, or a frame from a newer build, shows the summary; the older-build badge. ## 6. Client

The client renders a view and sends intents, so there's little logic to unit test, and that's by design.

Most `web` tests run in node with no DOM. A file that needs one opts in with `// @vitest-environment jsdom` on its first line and renders with Testing Library (`@testing-library/react`, `user-event`); everything else stays in node. jsdom has no layout, Web Animations, `matchMedia` or `ResizeObserver`, so such a file stubs them (see `web/tests/hud/readMarking.test.tsx`) and lists in its header what it therefore can't check.

- **Pure layout math** (`web/tests/iso/placement.test.ts`: projection, paint order, standing spots, wall occlusion, walls joining with no gaps across the whole ship, `hitTest`, walking paths and facing; `web/tests/iso/scene.test.ts`: the renderer-neutral scene description, which effect wins (fog, hover, selection), poses, walk cycles, outlines and animation timing; `tools/tests/shipLayout/pages.test.ts`: repacking oversized sheets (the layout test also checks the committed pages pixel for pixel). `web/tests/iso/pixiEffects.test.ts`: which Pixi looks need a filter and that equal looks share one (tints, glows and timings are tuned by eye, not pinned). The Pixi renderer itself has no unit test (it needs WebGL); `npm run screenshot` drives it in headless Chromium (WebGL through SwiftShader), and context loss, StrictMode and hot reload were checked once by a scratch Playwright script (lose and restore the context while walking; edit `PixiRenderer.ts` with the page open), not a standing test; `web/tests/iso/useActingOn.test.ts`: which queued action just began, and what an action is aimed at; `web/tests/scene/plan.test.ts`: the minimap's paths and dot placement). *Covered.*
- **Chat read marking** (#400, #403; `web/tests/hud/readMarking.test.tsx`, jsdom): focusing or clicking a row marks it and counts never fall, a click in the portalled "⋯" menu or on a thread's starter marks nothing more; ArrowUp/Down, Home and End move between rows and mark them, keys on a row's own controls are left alone, Tab lands on the first unread row (else the last); a new message marks the channel only on the latest page, with layout, in a visible focused window, and never on mount or when history first becomes readable; no provider doesn't throw; Mark all read shows only with unread on the active tab and raises that tab's channels. A replay (no store) and an ended game show no tab badges or chips. `web/tests/announce.test.ts`: the announcer's "N new in …" count comes from the store. The pure parts are in `feedKeys.test.ts` and `chatRead.test.ts`. *Covered.* *Not covered:* real layout of CSS-hidden tabs and the phone panel (jsdom's boxes are stubbed), Safari not focusing on click, real `:focus-visible` (jsdom matches it on a mouse focus too).
- **"New messages" divider, unread bar and chips** (#400; `web/tests/hud/unreadDividerDom.test.tsx`, jsdom, and `unreadDivider.test.ts`): the divider goes at the read count when the channel opens and stays as you read, is placed fresh on each opening and not while another channel is on screen, appears for unread that arrives unmarked, never above only your own messages; sending and Mark all read drop it; the bar offers a jump to an earlier page and goes once there; chips show one channel's unread with the count in the row's name; `unreadByFeature` files shared planets and reports under their feature. *Covered.* *Not covered:* the bar for a divider scrolled above the feed, and the scroll and keyboard focus after Jump (jsdom has no IntersectionObserver or layout); a jump to a page that must be fetched.
- **Markdown rendering** (`web/tests/hud/Markdown.test.tsx`): bold, headers, lists, links and HTML dropped, read-only checkboxes. *Covered.*
- **Tips** (`shared/tests/tips.test.ts`: each tip's trigger and the room it names, End cycle only where offered, none for the dead; `web/tests/tips.test.ts`: dismiss, snooze until the situation ends, mute, stored prefs read defensively). *Covered.*
- **`targets.ts`** (#116; finding the selection in a view, actions on a target, attack weapon, and action labels): pure and cheap to test. *Covered* in `web/tests/hud/targets.test.ts` (action description in `web/tests/hud/actionText.test.ts`, button labels and odds in `web/tests/hud/ActionLabel.test.tsx`).

A real-browser test, run by `npm run test:browser` and not by `npm test` or `verify` (about 50s): it starts Vite in-process, opens the lobby in headless Chromium (Playwright), and fakes the matchmaker websocket, so it needs no dev servers. *Covered.*

## 7. Internationalization (English, French, Spanish)

Checks live in `tools/tests/i18n/` (scanners in `tools/src/i18n/`) and run with `npm test`. Catalogs are `web/src/locales/{en,fr,es}.json` merged with `shared/src/locales/names.{en,fr,es}.json` (rooms, equipment, items, skill names; i18next JSON v4; English is the reference).

- **Catalog parity:** every language has the same keys, no empty values, the same `{{placeholders}}` and Trans tags, and every plural form its language needs (French and Spanish need `_many` as well as `_one`/`_other`; English doesn't). *Covered* by fixtures and the real catalogs (most of the client and the game text are translated; what isn't is in the baseline below).
- **Runtime language switching** (`web/tests/i18n/i18n.test.ts`): saved choice beats browser language, startup is synchronous, switching changes `t()` output, persists, and updates `<html lang>`. *Covered.* The picker itself (`LanguageSwitcher`, in the lobby and the settings dialog) has not been checked visually.
- **Keys in use exist:** every static `t("key")` / `i18nKey` in `web/src` is in the English catalog. *Covered.*
- **No new hardcoded text (ratchet):** `baseline.json` records how many hardcoded English strings each file has (client JSX text and attributes, and the sentences, errors, and names in `shared` and `server`). A file may not gain any, and when it loses some the test fails until the baseline is lowered (`UPDATE_I18N_BASELINE=1 npm test -w tools -- i18n`). The scanners are regex heuristics: a line that should stay English carries an `i18n-ignore` comment. *Covered.*
- **Moderation with accents:** `\b` ignores é/ñ, so blocked words with accented edges aren't masked (`it.fails` in `moderation.test.ts`). *Known gap.* Also: the word list is English-only.
- **Not covered yet:** a test that every room and equipment type in `Mush/derived/ship-rooms.json` has a catalog entry (today all 27 rooms and 28 equipment types do, but nothing enforces it, and the derived JSON still carries English `label`s); pseudo-locale and fr/es screenshot passes (need the `t()` seam and a language switch); layout overflow with longer French and Spanish text.
