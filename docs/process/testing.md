# What to test, and why

The project's main risks, roughly in priority order: hidden information leaking to the wrong seat, untrusted input (clients, chat, and later model output) getting further than it should, rules that quietly break as features are added, and the game stalling. Tests should go where those risks are. This is a checklist, not a coverage target.

Status: **covered** = tests exist, **partial** = some exist, **missing** = none yet. Tests live in a `tests/` folder next to `src/` in each package (`shared/tests`, `server/tests`, `tools/tests`, `web/tests`; the one exception is `tools/src/death/hpWrites.test.ts`). Server tests (`server/tests/`) run `GameRoom` and `Matchmaker` under plain Vitest: `partyserver` is replaced by `FakeServer` via `vi.mock`, with fake storage and sockets in `server/src/testing/fakes.ts`. This doesn't exercise the real Durable Object runtime (`@cloudflare/vitest-pool-workers`, not installed; ask first). Most server risks can instead be tested by pulling the decision out into a pure function, as `server/src/rateLimit.ts` already does.

Keeping rules tests from breaking for the wrong reasons: shared helpers live in `shared/tests/support.ts` (seats, player lookup, applying actions, advancing cycles, and reading what a view offers through `offered`/`option`/`costOf`), so a change to `Seat`, `ActionResult`, or the shape of `PlayerView.actions` is fixed in one file. Each feature pins its confirmed numbers in one test and derives them from `state.config` everywhere else. Hidden-information tests are the exception and stay strict: they should break when a view field changes. The tests in `shared/tests` are not typechecked (`shared/tsconfig.json` includes only `src`), so a type error there shows up only when the test runs.

## 1. Hidden information (highest priority)

A leak can't be fixed after the fact: once a client has seen a role, the game is spoiled. Leaks also don't show up as bugs, since everything still looks fine on screen.

- **`viewFor` strips everything a seat shouldn't see:** other players' roles, HP, morale, and inventories; other rooms' items, equipment, and log history; private log entries; the RNG state. *Partial* (`rules.test.ts`, `items.test.ts`, `examine.test.ts`, plus targeted checks that contamination, spore state, and private log lines are in no other seat's view in `infection.test.ts`, `skills.test.ts`, and `heal.test.ts`; `death.test.ts` checks that a dead player's view has nothing room-based and no one else's role or contamination, and that nobody's view gives a dead player's room; `planets.test.ts` checks that another player's planets, scan failures, and your own unrevealed sector tags are in no view). The blunt test is in `leaks.test.ts`: every hidden value in a four-seat game is a unique sentinel, and each seat's serialized view must contain exactly the sentinels it may see, so a leak through a field nobody thought to check still fails. Every field of `GameState`, `PlayerState` and `ItemState` is listed in `shared/tests/leakFields.ts` with who may see it and the test that checks it; a new field fails `leaks.test.ts` (keys of a real game) and `tools/tests/leaks/fields.test.ts` (the interfaces in the source, so optional fields too) until it is listed (#102). Values that can't be made unique (roles, enums, player ids, such as `cheats` or `room`) rely on the targeted test named there.
- **Error messages don't depend on hidden state.** `applyAction` and `queueAction` answer `illegal_action` whatever the reason (`rules.ts`, `queue.ts`), and the room passes on a generic error (`GameRoom.test.ts`). A message like "can't target a Mush" would leak a role through the error channel. `errors.test.ts` (#103) checks refusals that turn on hidden state (spiking a Mush, the crew's daily spore cap, a partner who has already shared today) against ones that don't, both at once and queued, and first checks each case hits the refusal it names. It covers the error text only: that an action is refused at all can still give something away (see the note in the file). *Covered.*
- **Action bars and queues** (`queue.ts`): your action under way and your queue are in your view only; others get a `busy` bar (times, never the action) only in the actor's room and only when the action's log entry could reach them (private never, covert only on camera). *Covered* (`queue.test.ts`). Not covered, and not new: every accepted input, ticks included, re-sends a view to every connection, so message timing says that someone did something.
- **Channel plans** (`plans.ts`): only a channel's members get its plans, a stopped holder's reason is only in their own log, and the author's view after a summons has nothing about rooms but theirs. *Covered* (`plans.test.ts`, the `planRoom` sentinel in `leaks.test.ts`). The `postPlan` message: parsing with known keys only and malformed drafts refused (`protocol.test.ts`), recording, a non-creator refused, the chat rate limit and a rebuild from the record (`GameRoom.test.ts`, "GameRoom plans").
- **Each connection gets its own seat's view** (`GameRoom.broadcastViews`). A mix-up here (one view sent to everyone, or the wrong `playerId` in a connection's state) would leak everything, and no rules test would catch it. *Covered* (`GameRoom.test.ts`).
- **Seat tokens.** A missing or unknown token is rejected (close code 4001). A valid token maps to exactly one seat. The matchmaker sends each human only their own token, never a broadcast. A token is effectively the seat itself, so whoever holds it can play that seat and see its view. *Covered* (`GameRoom.test.ts`, `Matchmaker.test.ts`).
- **Bots see only their own seat's view.** This is structural today (`viewFor(game, botId)` in `scheduleBots`; `WanderBot` is tested to pick only from its own view's legal actions in `bots.test.ts`). The model bot's prompt is tested to be unchanged by anything hidden from its seat (another player's role, HP and morale, another's private log entry, another room's history) and to change with the seat's own state (`model.test.ts`). *Covered.*

## 2. Untrusted input

Everything from a client is hostile until parsed. Player text will also become model input.

- **Wire parsers** (`parseGameMessage`, `parseMatchmakerMessage`): reject malformed JSON, wrong types, extra or unknown action kinds, and oversized strings, and never pass through fields that weren't validated. *Partial*: the cases are scattered through the feature tests (`cook`, `heal`, `bonds`, and `channels` tests parse their messages, including `toggleCheckbox` and channel names), `GameRoom.test.ts` checks that garbage gets "Malformed message", and `Matchmaker.test.ts` that a malformed queue request is rejected. There is no table of bad inputs per message type, and the 24-character name cap (`MAX_NAME_LENGTH`) has no test. This would suit a small table.
- **Legality is the server's call.** `applyAction` rejects any action not in `legalActions(state, player)`, including well-formed actions for another player's item, a non-adjacent room, or a dead player. *Partial* (`actions.test.ts` checks unaffordable and non-candidate actions; `punch`, `spike`, `death` and other feature tests check illegal uses leave state unchanged).
- **Chat moderation** (`moderateChat`): invisible characters, links, masked words, length limits. *Covered* for the basics. Grow the cases as abuse turns up.
- **Player names** are trimmed and capped at 24 characters (`parseMatchmakerMessage`) but not moderated (only chat goes through `moderateChat`). No view carries them during a game (people are known by character), but they will be shown once games can end. They go through `moderateChat` (as `moderateName`) when the end screen shows them (owner, 2026-10-22). *Covered* (`victory.test.ts`).
- **Rate limits:** the per-connection message limit, and a per-seat chat limit that survives reconnecting. *Covered* (`rateLimit.test.ts`, `GameRoom.test.ts`). The sign-in and account routes (#305), with the binding faked: an OAuth start redirects with `rate_limited` before touching the provider, `/api/*` answers 429 with `Retry-After`, keys are the account when signed in and the IP otherwise (also for an expired session), only sign-ups count against the new-account limit, logout and the callback are never limited, dev servers spread keys, and a failing binding lets requests through. *Covered* (`auth.test.ts`). *Not covered:* the client keeping its account state on a 429 (`useMe`; the web tests can't run hooks), and the real binding (checked on staging).
- **Model output:** garbage, an action that isn't legal, or a prompt-injection attempt has to end up as a legal fallback action, never an unchecked one. `parseChoice` takes only a goal number in range and `ModelBot` chooses by priority otherwise; a chosen goal runs with no further calls until it ends or an interrupt fires; chat can't break out of its quoted line in the prompt (`model.test.ts`). *Covered* for goal choice; model-written chat doesn't exist yet. `GoalBot` returns only actions its view offers, even when a goal's step is stale (`goals.test.ts`, including long seeded runs).

## 3. Rules correctness

The rules will grow the most (infection, win conditions), and every addition can break an older rule.

- **Each rule's numbers** (AP/MP costs and caps, cycle gains, slot counts, and the per-feature `cost`, `effect` and `successChance` values) against the confirmed values in `config.ts`. *Covered* for what exists; the feature tests read them from the nested `state.config`.
- **Determinism:** the same seed and inputs give the same state. Persistence and replays depend on it. *Covered* (`rules.test.ts` for the same seed, and `replay.test.ts`: random games across a day boundary, with chat and private channels, replayed from JSON-stored inputs must equal the live state, and a ship launched empty in pre-selection through its joins; a rejected input makes the replay throw. Every input type is generated except cheats, which `cheats.test.ts` replays, and `createThread`. `GameRoom.test.ts` checks that the stored snapshot is exactly what `rebuildGame` makes of the stored record, with bots, ticks, a cycle and chat, so a state change that bypasses the record fails it).
- **The RNG moves on and rules read the game's own config.** A roll that drops the next RNG state repeats the same draw; a rule that reads `DEFAULT_CONFIG` ignores a game's own config. *Covered*: rule code draws through the `roll`, `rollInt`, `rollFloat` and `rollShuffle` helpers in `rng.ts`, which advance `state.rng` themselves (`rng.test.ts`); only seeded generators that take a bare seed (`planets.ts`, `createGame`, `singlePlayerGame`) use the pair functions, and return the next state to their caller; Biome bans importing `DEFAULT_CONFIG` in `shared/src` (only `singlePlayer.ts` may, with a `biome-ignore`); `self_disease.test.ts` checks both for disease durations.
- **Every module loads on its own.** An import cycle crashes only when it is entered at the wrong module, which depends on what a test file imports first. *Covered* (`moduleLoad.test.ts` loads each `shared/src` file first into an empty module graph).
- **Purity:** `applyAction` never mutates its input, and failed actions leave the state unchanged. *Covered* (`rules.test.ts`, `items.test.ts`, and the per-feature tests).
- **State survives a JSON round trip** (`JSON.parse(JSON.stringify(state))` deep-equals the original). State is persisted and cloned via JSON, so an accidental `Map`, `Set`, `Date`, or `undefined` would silently corrupt games. *Missing.* Some tests copy state through JSON to check that an action doesn't mutate it, but none asserts that a round trip returns an equal state, and the persistence test uses fake storage that keeps the objects as they are.
- **Every legal action succeeds.** Anything in `legalActions` must be accepted by `applyAction`; the client and bots trust that list. *Partial* (feature tests apply the actions they expect to be offered; nothing walks the whole list).
- **0 HP always kills** (`death.test.ts`, plus `tools/src/death/hpWrites.test.ts`, which scans the rules source and fails if any file outside its allowlist (`death.ts`, `cheats.ts`, `actions/heal.ts`, `actions/consume.ts`, `hunters.ts`) writes `.hp`). *Covered* for punch (`punch.test.ts`), hunger (`statuses.test.ts`), and showering (`shower.test.ts`).
- **Invariants under random play:** run many seeded games with `WanderBot`-style random legal actions and check after every step that each item is in exactly one container, AP and MP stay within their caps, nobody is in a room that doesn't exist, and the game always offers someone a legal action. This catches combinations nobody wrote a test for. *Missing.*

## 4. The server keeps the game going

A stalled or wiped game is the most visible failure for players.

- **Persistence:** a restarted room restores the game, tokens, and input count, and continues the input record; a save with a different `STATE_VERSION` is dropped, not loaded half-broken, while its record (`setup`, inputs, blocked text) is kept and never launched over. The snapshot stores config overrides, not the config, for every way a room launches, and a reload resolves the config again, picking up a `DEFAULT_CONFIG` edit but not a `PRESELECTION` one, and equipment changed during a game survives it. `FakeStorage` copies values in and out like Durable Object storage. *Covered* (`GameRoom.test.ts`, `shared/tests/config.test.ts`; the overrides' shape is in the `stateShape.test.ts` fingerprint). Restoring the bots after a restart is not tested.
- **Timed actions keep going:** an action is stamped with server time, an alarm is set for its end, and the alarm's tick does it; a room restored mid-action finishes it from the stored alarm; Clear queue removes the alarm. *Covered* (`GameRoom.test.ts`; rules in `queue.test.ts`, replays with ticks in `replay.test.ts`). Bots waiting for their bar is not tested at the room level.
- **Bots never stall the game.** A bot isn't scheduled twice. A bot whose chosen action is illegal is logged (`console.warn`), told through `Bot.refused` (a `GoalBot` drops that goal for the cycle), and doesn't crash the room. A `decideAction` that throws or hangs needs a fallback. A throw inside the `setTimeout` in `scheduleBots` is caught and logged, and a bot stays pending until its decision finishes, so a slow model call isn't asked twice (tested). Model calls time out (`ModelGate`), and a failing model leaves model bots playing scripted (tested). A bot that throws is not tested at the room level. *Partial.*
- **Matchmaker:** the first player is boarded at once on a newly launched ship with no bots; later players join the same open ship; a full or closed ship is replaced by a new one; the deadline alarm forgets the open ship; the open ship survives a restart; simultaneous joiners board one at a time; each player gets only their own token; a taken character is refused. *Covered* (`Matchmaker.test.ts`). Dev-only bot filling (`GameRoom.fillWithBots`) is not tested.

## 5. Data and tooling

- **Generated files are current:** `ship-art.json`, `ship-rooms.json`, and `ship-plan.json` match their sources, and `ship-map.json` is in its one-tile-per-line format. *Covered* (`tools/tests/shipLayout/`).
- **The ship map editor** (`web/src/editor/`): its scene is what the game draws at fog depth "all", it names each sprite's map tile and turns pixels into cells as `gridToPx` turned around (`shipScene.test.ts`); its edits change only what they should, keep the old map for undo, move by the arrow keys' screen directions, and pick a new tile's kind and room, and move a whole room (`edits.test.ts`); its checks find doors with no room, no floor or no way back, floor on floor and equipment with no tile, and point at the tile and cells to fix (`checks.test.ts`); a save is refused unless `validateMap` passes, which is tested on bad maps and run on the committed one (`tools/tests/shipLayout/shipLayout.test.ts`). *Covered.* The component (pan, zoom, selecting, saving through the dev server, the checks panel and jumping to a problem) was checked in a browser by hand, not by a test.
- **The ship map is sound:** every door goes both ways, and every room can be reached from the start room. *Covered* (`tools/tests/shipLayout/shipLayout.test.ts`, `rules.test.ts`). The minimap plan has the same doors as the rules' room graph.
- **Converter edge cases:** slices past their sheet, equipment bound to unknown slices. *Covered* (`shipLayout.test.ts`).
- **The hand-edited map is consistent:** every tile's slice and frame exist, equipment binds only known slices, doors have targets, no room overlaps another (`ship-check`), and no wall stops just short of another room's. *Covered* (`shipLayout.test.ts`, `check.test.ts`, `web/tests/iso/placement.test.ts`). Not covered: how it looks at fog depth 1 and 2, where rooms beyond aren't drawn.
- **Account storage** (`server/src/accountStore.ts`, D1): every migration applies in order to a fresh database and files are numbered without gaps; names are unique ignoring case; a failed statement in a batch leaves nothing behind (account plus identity, rename plus history); renames are limited to one per 24 hours and free the old name; an expired session cannot be renewed; only a session ID's SHA-256 is stored, and sessions expire, renew and delete; an account is aboard one ship at a time, and leaving or ending a ship frees it. *Covered* on node:sqlite (`accountStore.test.ts`, through `server/tests/sqliteD1.ts`, which has no exec or transactions so the store can't rely on them), plus a smoke test that applies the migrations with wrangler to a throwaway local D1 and runs each statement once on D1 itself (`accountStore.d1.test.ts`). Migrations are append-only: CI fails a push to `main` that modifies, renames or deletes one (`.github/workflows/ci.yml`).
- **Sign-in and display names** (`server/src/auth.ts`, `oauth.ts`; `shared/src/accounts.ts`): a callback whose state doesn't match the browser's cookie (or was started for another provider) is refused before contacting the provider; the state cookie is single-use; Google gets PKCE; no account exists until the name is confirmed; a suggested name that fails `checkDisplayName` or was taken starts empty; taken (ignoring case), rejected and empty names are refused; linking refuses an identity owned by another account and a session that changed since start; a session renews only under 15 days left and expires; logout is per device, POST only, and ends a pending sign-up; signing in with a new identity signs the device out first, and a known one ends a pending sign-up; one identity per provider per account; a body without `Content-Length` or over 1 KB is refused unread; rename once a day, freeing the old name, with `name_unchanged` not using up the day; deployment cookies are `__Host-` and Secure, dev ones port-named. *Covered* in `server/tests/auth.test.ts` with a fake provider on node:sqlite, and `shared/tests/accounts.test.ts`. *Not covered:* a real Google or Discord round trip (manual, once the owner's OAuth apps exist), and the Vite proxy (checked by hand: `/api`, `/auth` and the `/parties` WebSocket go through it, and wrangler sees the page's origin).
- **Setups** (#233; `shared/src/setups.ts`, `server/src/setupStore.ts`, `setupRoutes.ts`): strict parsing of knobs, per-language text and posts (unknown fields and languages refused); moderation masks the word list in every field and rechecks the caps after removing links; 50 new setups per account with versions free, 500 posts in all; versions number along the chain and only the owner's newest version gets one; the list shows only the newest version, and one that stops validating drops off it but is still found by ID; the owner's current name is shown; reading is public, posting needs an account and is rate limited per account; no response holds an account ID. The D1 smoke test runs each statement, including the unique-index error. *Covered* (`shared/tests/setups.test.ts`, `server/tests/setups.test.ts`, `accountStore.d1.test.ts`).
- **Dev sign-in** (#287): refused without `DEV_SERVER` (even with `ALLOW_CHEATS`), refused on a non-localhost host, never reaches an account through a Google or Discord identity, and reuses its account by name. *Covered* in `server/tests/auth.test.ts`.
- **Finished games list** (#155; `server/src/gameStore.ts`, `gameRoutes.ts`, `GameRoom.ts`): a running game produces no entry; a game is written once, and a failed write is retried from the alarm until it lands; start and end roles and characters are recorded across a conversion and a Transfer (alpha and beta Mush), and every seat is human at the start when the game ended before the Mush were chosen; a single-player game is recorded only with an account and never listed publicly; games stored before the list existed are never listed; paging is newest first and stable when a game ends between pages; the page size is capped; a cursor the server didn't make is refused; no response holds an account ID. The D1 smoke test runs each statement. *Covered* (`gameStore.test.ts`, `GameRoom.test.ts`, `accountStore.d1.test.ts`). *Not covered:* the `/games` page (checked by hand), and a game ending through a real input in the room tests (they set the phase directly).
- **Replay copy to R2** (#336): a finished game's history is copied once, as per-cycle chunks that each rebuild by themselves and together rebuild the whole history and the game's last full view; a chunk holds only each input's time and history; `replayReady` stays false until every chunk and the index are written; a failed copy (partway or at the index) retries from the alarm, and a room revived after a failed copy finishes it; the record stays in room storage. *Covered* in `replay.test.ts` (chunking) and `GameRoom.test.ts` (with `FakeR2Bucket`). *Not covered:* real R2 and workerd's `CompressionStream` (Node's runs in the tests); not yet tried on a deployment.
- **Accounts on ships** (#285): multiplayer refuses a socket without a valid session, including one that ended after connecting; the seat takes the account's name; one ship per account across languages, with a second join resumed onto the same seat; a refused seat closes its D1 row; a dead or ended seat frees the account, and every row closes when the game ends; the account ID is never in the game, the replay inputs or a view; the record's `account:<seat>` entry keeps it for moderators through a rename and a dropped snapshot, and each chat input records its message id (#292); logout (or another account signing in or signing up on the device) revokes only that session's tokens and closes its sockets, and still signs out (or in) if the revoke fails; the sweep closes stale rows and leaves young ones; the action rate limit is per seat. *Covered* in `Matchmaker.test.ts`, `GameRoom.test.ts`, `auth.test.ts` and `shipSweep.test.ts`. *Not covered:* the real cookie on a WebSocket upgrade through the Vite proxy and workerd (checked by hand with `npm run dev`).

## 6. Client

The client renders a view and sends intents, so there's little logic to unit test, and that's by design.

- **Pure layout math** (`web/tests/iso/placement.test.ts`: projection, paint order, standing spots, wall occlusion, walls joining with no gaps across the whole ship, `hitTest`, walking paths and facing; `web/tests/iso/scene.test.ts`: the renderer-neutral scene description, which effect wins (fog, hover, selection), poses, walk cycles, outlines and animation timing; `tools/tests/shipLayout/pages.test.ts`: repacking oversized sheets (the layout test also checks the committed pages pixel for pixel). `web/tests/iso/pixiEffects.test.ts`: the Pixi renderer's looks, which filters are shared, padding, and the outline pulse. The Pixi renderer itself has no unit test (it needs WebGL); `npm run screenshot` drives it in headless Chromium (WebGL through SwiftShader), and context loss, StrictMode and hot reload were checked once by a scratch Playwright script (lose and restore the context while walking; edit `PixiRenderer.ts` with the page open), not a standing test; `web/tests/iso/useActingOn.test.ts`: which queued action just began, and what an action is aimed at; `web/tests/scene/plan.test.ts`: the minimap's paths and dot placement). *Covered.*
- **Markdown rendering** (`web/tests/hud/Markdown.test.tsx`): bold, headers, lists, links and HTML dropped, read-only checkboxes. *Covered.*
- **`targets.ts`** (finding the selection in a view, `actionLabel`): pure and cheap to test. *Missing.*
- **Lobby panel keeps its size** (`tools/tests/lobby/lobby.test.ts`): joining a ship must not resize the panel, on desktop and a 360px phone, in en/fr/es. A real-browser test in `npm test`: it starts Vite in-process, opens the lobby in headless Chromium (Playwright), and fakes the matchmaker websocket, so it needs no dev servers. *Covered.*
- **Layouts, mobile, and touch** are checked with the `play` skill's desktop and 360px phone screenshot passes, not unit tests. The script already fails on sideways page scroll. The on-screen keyboard can only be checked on a real phone.

## 7. Internationalization (English, French, Spanish)

Checks live in `tools/tests/i18n/` (scanners in `tools/src/i18n/`) and run with `npm test`. Catalogs are `web/src/locales/{en,fr,es}.json` (i18next JSON v4; English is the reference).

- **Catalog parity:** every language has the same keys, no empty values, the same `{{placeholders}}` and Trans tags, and every plural form its language needs (French and Spanish need `_many` as well as `_one`/`_other`; English doesn't). *Covered* by fixtures and the real catalogs (most of the client and the game text are translated; what isn't is in the baseline below).
- **Runtime language switching** (`web/tests/i18n/i18n.test.ts`): saved choice beats browser language, startup is synchronous, switching changes `t()` output, persists, and updates `<html lang>`. *Covered.* The picker itself (`LanguageSwitcher`, in the lobby and the settings dialog) has not been checked visually.
- **Keys in use exist:** every static `t("key")` / `i18nKey` in `web/src` is in the English catalog. *Covered.*
- **No new hardcoded text (ratchet):** `baseline.json` records how many hardcoded English strings each file has (client JSX text and attributes, and the sentences, errors, and names in `shared` and `server`). A file may not gain any, and when it loses some the test fails until the baseline is lowered (`UPDATE_I18N_BASELINE=1 npm test -w tools -- i18n`). The scanners are regex heuristics: a line that should stay English carries an `i18n-ignore` comment. *Covered.*
- **Moderation with accents:** `\b` ignores é/ñ, so blocked words with accented edges aren't masked (`it.fails` in `moderation.test.ts`). *Known gap.* Also: the word list is English-only.
- **Not covered yet:** a test that every room and equipment type in `Mush/derived/ship-rooms.json` has a catalog entry (today all 27 rooms and 28 equipment types do, but nothing enforces it, and the derived JSON still carries English `label`s); pseudo-locale and fr/es screenshot passes (need the `t()` seam and a language switch); layout overflow with longer French and Spanish text.
